# Authorized transactional delivery

When managed execution is selected, the existing dispatcher also checks
[managed admission](../management/admission.md) before new inbox/application work
and at the actual callback boundary. Unadmitted application messages requeue after
original owner cleanup; admitted work, native replies and committed outbox
settlement retain their existing lifetimes. This gate does not replace native
authentication, capability checks, inbox arbitration or transaction completion.

Register an event or command subscription with an explicit codec, scoped handler factory, capability list and trusted target resolver. The logical receiving identity is `(Application, Environment, Subscription, MessageId)`. Replicas compete on that same identity. Separate event subscriptions retain separate inbox protection and each receive the event; a command route has one logical subscription.

The dispatcher borrows native bytes while waiting for process-wide work and encoded-byte admission. Ordinary saturation waits cooperatively before copying or decoding. A finite shared waiter bound of at least 128 covers the supported 16 subscriptions with eight native callbacks each. Exhausting that hard bound is an explicit overload failure that visibly stops the affected consumer. Shutdown cancels admission waits, awaits the independent native requeue and joins accepted work. It never releases an in-use buffer or DI scope merely because cancellation was requested.

Encoding uses a small growing segmented buffer whose cumulative allocated capacity is capped at twice the selected maximum envelope size. It rejects a writer request before another segment can cross that bound, including JSON-escaped metadata under a tiny payload profile. Flattening allocates the final owned wire once and parses its metadata/payload from that same array. The writer segments, final wire and owned codec payload together fit the existing four-envelope staging reservation; small messages do not preallocate the maximum capacity.

For each admitted valid envelope, the transport's private native evidence establishes a new `SecurityHostContextScope` and independent DI scope. Actual mapped caller identity overrides producer audit fields. The codec and target resolver run in that scope, then capabilities are checked against the actual resource before opening the original ReadCommitted owner. An unsupported schema, denied identity, changed immutable digest or conflicting provenance uses separate rejection responsibility and cannot claim a legitimate canonical inbox identity.

The store arbitrates the inbox under the original explicit context. Only an acquired attempt constructs and invokes its handler. Handlers execute outside native SQL callbacks and borrow `MessageHandlerContext.Transaction`; they do not commit it. Business SQL, outgoing messages and processing completion participate in that same transaction. Existing handled or secured dispositions suppress duplicate effects. A successful store method alone never authorizes acknowledgement: the owner must actually return `Committed` and finish disposal first.

`IMessageHandler<T>` handles ordinary events and commands. A durable command uses `MessageRequestSubscriptionDefinition<TRequest,TResponse>` in durable mode, and a command envelope carries `MessageOperationReference` without requiring a reply waiter. The dispatcher resolves the existing registered Operations scope/resource and retains that exact binding with the inbox. It installs a narrow guard on the exact original context. The actual Operations service resolves again and checks the guard before authorization, journal access or effects; drift poisons the owner. The public Operations API and its one-shot original-context admission remain unchanged.

The durable visitor invokes Operations once. `Prepared` and `Replayed` remain separate Operations facts and neither asserts transaction commit. A new MessageId with the same business key and canonical input can secure a new inbox result by replaying the original operation without another business effect. The same key with changed business input becomes a canonical protocol terminal outcome. A repeated MessageId with changed wire bytes is instead a transport-content rejection.

Trusted retry/redrive ingress is authenticated as the current delivery service and requires current subscription and retry capabilities. Exact digest, original provenance, operation binding and the eligible stored handoff/ordinal/generation are checked before execution. Older verified ordinals may observe an already secured disposition under store arbitration; they cannot reacquire effects or schedule another chain. An optional `MessageRetryValidator<T>` receives the current caller plus retained original audit facts before execution or replay disclosure, so application rules can require live original-producer reauthorization without impersonating that producer.

After a known rollback of an acquired failed attempt, the separate disposition coordinator may commit exactly one retry or terminal handoff. Original persistence `Unknown` never becomes an assumed rollback or a second scheduled ordinal. Infrastructure failure before acquisition does not consume a handler attempt. Native acknowledgement follows original-owner, disposition-owner and security-scope cleanup. A broker acknowledgement fault propagates unchanged and cannot be reclassified as a handler failure after a known business commit.

`MessagingReplies` is a reserved native ingress subscription, independent of claimed wire purpose. Applications cannot register a subscription with that alias. The selected request coordinator uses this dispatch path for typed replies and current-attempt recovery. Initial denial replies link to separate rejection responsibility; canonical terminal replies retain their exact outgoing reference in the same transaction. Reply admission checks current native responder authority and the exact request-wire digest as well as attempt and endpoint identity. See [typed requests and recovery](requests.md). Part A delivery results alone do not establish these Part B facts.

The optional shared instrumentation measures one admitted delivery through transaction, disposition, scope and native acknowledgement settlement. Publication timing measures actual native publication settlement. Fixed outcomes and registered aliases remain bounded; telemetry failures cannot alter business responsibility.

The unit cases reuse `CIS.CommonTesting` completion scripts and the existing controlled security projector to verify orchestration, cancellation, admission, scope cleanup, exact faults and resolver drift. They are not SQL or broker durability evidence. The focused combined cases use the explicitly owned PostgreSQL and RabbitMQ fixtures for concurrent two-root inbox arbitration with a non-idempotent SQL counter, distinct subscriptions, runtime reconstruction, separate rejection protection, real commit followed by simulated loss of its completion evidence, and the existing RM-03 journal. The completion-loss seam occurs after a real native commit; it is not a broker/database outage or deployment failover proof. See [testing](testing.md) for the separate typed reply, receipt and process-death fixtures, and [verification](../../changes/CIS-0019/verification.md) for their actual executed results and limits.
