# Application inspection in the Management portal

Applications lead with their permitted display name, application identity and environment. Instance rows show the reported instance label, that registration's reported application version and its dated presence. A UUID used as a reported label is shown as an unnamed reported item; its exact original value remains in Technical details. The portal does not manufacture a friendly name or a fleet-wide current version.

The permitted application description appears directly beneath its title when present. Current and Past instance sections retain all reported fields when a desktop window is resized; constrained tables scroll within their own frame rather than widening the whole page. Past means explicitly closed registrations, while missed or unknown presence remains in Current without a process-exit claim.

Application, registration, source, binding, execution-scope, job and report identities remain available under collapsed **Technical details**. Expand the disclosure with its summary control, then use the field's **Copy** button. Copy retains the complete disclosed string and announces success or an unavailable clipboard. Closing a details panel with Close or Escape returns focus to the selected row, or to the heading if that row disappeared. Technical disclosure is subject to the same protected read/session lifetime as its record; it is not another permission boundary or a way to retain denied values.

The **Capabilities** tab separates three application feature groups: Schedulable job types, Registered RuleEngine instances and Trigger providers. The currently selected service supplies no trusted logical definition/participation catalog for these groups. They therefore say **Unavailable**. This is not an empty successful feature set, and no Create, Configure, Run or Cancel action is inferred. Typed portable catalog contracts alone do not establish a deployed catalog backend.

Collapsed **Service API details** preserves the actual Management HTTP descriptors and advisory caller hints. Not evaluated, Allowed and Denied remain distinct. These diagnostics describe HTTP APIs; they are not application job types, RuleEngine instances or trigger-provider definitions, and opening one never invokes that API. The public Management capabilities protocol is unchanged.

**Scheduled jobs** continues to inspect one selected instance inventory report at a time. Job/category display names, reported modes, resource observations and reported local configuration remain telemetry. They do not install a schema, establish an executable handler, define a configured Scheduled Task or prove a schedule, current lease, execution history or semantic definition version. The displayed application version belongs to that report's registration. Logical definition versions and separately observed participation remain unavailable until their actual native owner is delivered.

Job details retain the exact registration, report sequence, execution scope, job, resource and mode in navigation. Observed and received timestamps remain separate, and the selected report's full registration/sequence can be inspected without replacing it with the latest report. If that exact relationship disappears from the bounded inventory page, the view explains that it is unavailable. Task, Event and history links retain their truthful unavailable explanations; inventory is not substituted for historical evidence.

Protected reads use the existing validated session/service associations and shared request lifetime. Session loss clears the affected views; late responses cannot refill a retired session or selected target. Transient outages can retain only the same permitted dated snapshot with an explicit earlier-observation notice. Inspection adds no scheduler runtime. The separate [display metadata editor](portal-metadata.md) uses current native grants, explicit review and original-key recovery.

Focused validation is located in the portal's `projection.test.mjs`, existing `native-host-consumer.mjs` and `native-browser-checks.mjs`. It covers diagnostic/catalog separation, readable-label preservation, reported version provenance, exact collapsed IDs, keyboard/focus and copy status, actual protected reads and absent feature support. Browser-controlled clipboard/race/paging cases remain labelled separately from native service/authentication observations; design screenshots and authored checks alone are not runtime acceptance evidence.
