# Logger outcome qualification

WP04-S05-T04 adds a complete reachable two-output outcome table to the actual Core logger. Shipping code, public API and dependencies are unchanged. The [shared catalog](../../../conformance/logging/logger-outcome-cases.json) has 125 literal cases: all 49 ordered pairs for direct and lazy calls, plus None before/after internal admission closure, differing console/file thresholds, capacity, sticky faults and throwing factories. Enabled output order is console then file; disabled outputs are omitted.

Each input declares numeric console/file thresholds (Trace=0 through None=6) and per-output capacity (null means unbounded for these controls). Debug union has console Warning=3 and file Debug=1; capacity cases explicitly select one console slot. Each output is an explicit non-I/O admission control. It has separate admission-method calls, total attempts, filtered/unavailable/full counts and accepted captures. Console tickets start after 10 and file tickets after 100. Only acceptance advances its own ticket. Initially faulted outputs differ from healthy outputs returning Faulted during admission; the latter become terminal so a subsequent call cannot retry their admission method. Faulted uninterested outputs remain Filtered. These controls never write files, create queues, deliver records or throw fake I/O exceptions.

Before calls, repeated IsEnabled queries must leave admission/payload observations unchanged. Capacity cases fill one slot and observe IsEnabled still true before QueueFull; they cannot reserve capacity. Each write records its own factory count. Interested factory failures preserve the exact original IOException object before capture or output bookkeeping. Early exits skip poison attribute/exception callbacks and factories. Accepted output bytes retain original payload after the caller changes its DTO; both accepting outputs receive the same capture and identical bytes.

Unit tests and exact-runtime child tests compare every literal result/counter/callback expectation. A Python runner independently checks original base64 bytes, strict UTF-8, JSONL framing, cap, controlled time/severity and owned payload. Nine altered-observation controls, including deletion of a required expectation field, must be rejected by each comparator. C# additionally checks complete ordered table coverage. Architecture checks require every case to map to a criterion. Comparators require all 17 base expectation fields, plus enabledAfterFirst for two-write scenarios. The [acceptance map](../../../conformance/logging/logger-qualification-map.json) preserves all four supplied criteria and binds current and prior qualification. T03 supplies InvalidEvent/global rejection and invalid-ticket protocol controls; T02 supplies argument/order/late-closure probes.

AC01-AC03 and the logger-owned parts of AC04 are qualified at the admission seam. **AC04 normal output I/O isolation remains pending WP05 real outputs/workers.** A Faulted status from a double cannot qualify that obligation. All four S05 task implementations may finish while full story acceptance awaits real integration. Internal CloseAdmission is used only as a test control; public StopAsync is not implemented here. Output-owned ticket/counter concurrency and overflow belong to real output work.

The [retained receipt](../../../planning/logging/evidence/wp04-s05-t04/receipt.json) records 264 new tests and all 3437 Windows Developer tests (2342 unit, 695 integration, 400 architecture), 59 compiler controls, and 125 actual native cases per platform with nine rejected controls each. All fourteen Developer stages pass; raw TRX, native bytes, inventory and failed earlier checks are retained. The earlier 125-case native candidate with eight controls is retained separately and does not qualify current changed inputs. Initial Claude technical review passed; its three coverage/portability findings were addressed before final verification. Final read-only Claude review passed with no blockers. T03 already executes valid-throw-valid recovery with original exceptions and following accepted tickets; the map links those retained cases. Native Ubuntu uses the same managed bytes with its real .NET runtime; this does not qualify the Linux SDK/full suite, macOS, mutation, compatibility, business or release families. The release profile and 41 Planned release cases retain their existing incomplete status.

## Native logger driver migration, 16 October 2026

The foundation, decision, capture and outcome Python drivers are retired. Native C# keeps all 256 scenarios and 28 legacy controls, with ten controls added to fill gaps in the existing native set. Parent checks bind physical PID/runtime/OS, exact fixture/Core/input bytes, complete parent state and no outputs. Foundation validation now retains the former schema, safe-error, clipping-prefix, full output/ticket-shape and fanout-byte assertions; capture/outcome readers require exactly two wire groups. [Migration evidence](../../../planning/evidence/corrective-loggers-migration-2026-10-16.md) records results. These are controlled internal capture/admission observations; per-output tickets here do not replace the current public incoming-acceptance contract.
