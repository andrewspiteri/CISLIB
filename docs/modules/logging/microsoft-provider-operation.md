# Microsoft scope operation identity

The exact ordinal operation_id key in a structured provider-created or borrowed host scope maps to typed operation identity when its value is a CLR string. Core trims it, treats blank as absent and validates at most 255 Unicode scalars without controls. Recognized strings and null are excluded from ordinary attributes. Null means absent; other non-string values, including Guid, integers and explicit LogValue.String objects, are invalid identifiers. Differently cased keys remain ordinary data. There is no ToString conversion. OperationContextData keeps its explicit typed OperationId property and unchanged attribute semantics.

The scope root is scanned once under the existing 1024-entry work guard. Recognized string IDs are metadata, so they can be read after the ordinary value budget is full if they occur within that guard. IDs in the unvisited tail beyond the 1024-entry guard are omitted with truncation provenance. Duplicate operation_id entries use the last visited valid metadata state, but any visited non-string/non-null ID rejects the whole capture. Blank or null metadata clears the frame ID so the outer nonblank ID remains eligible. Scope identity keys never become ordinary attributes. Superseded duplicates still consume bounded copy work rather than refunding the budget.

Within each store, inner attributes replace matching outer keys and the innermost nonblank typed operation ID wins. The existing Core/provider store is the outer layer and the borrowed host store the inner layer; the stores do not supply combined chronological ordering across arbitrary interleaving. Event attributes replace matching retained scope keys. Direct Core LogEventData.OperationId overrides scope identity when nonblank; blank falls back to the captured scope. An ILogger event-state field named operation_id remains an ordinary attribute and cannot replace typed root operation identity. The guide's recognized-string rule is scoped to scope state.

Explicit event keys take priority over remaining scoped keys under the aggregate budget; the provider numeric event_id is reserved through node and byte truncation. Typed operation_id remains part of the protected envelope. Invalid owned IDs throw before frame creation. An invalid borrowed ID rejects that event and increments InvalidEventCount once; it does not silently fall back to an earlier scope ID. The historically named host-omitted fixture now asserts rejection followed by a clean unscoped event. See the [current review addendum](review-contract-2026-10-15.md).

Names resembling service, env, version, component, resource, trace_id or span_id remain nested attributes. Neither scope nor event free-form state modifies automatic application/process identity or the W3C Activity-derived root pair. Those IDs remain frozen before cooperative host callbacks. The [scope capture guidance](microsoft-provider-scopes.md) records copied input timing, creator/LIFO ownership and borrowed-frame policy.

Twelve fixture modes cover copied/trimmed owned and host IDs, nested/blank scope and event precedence, duplicate/case/non-string inputs, explicit Core overrides, automatic identity and real Activity correlation, metadata after a full node budget, omitted metadata beyond the scan guard, invalid/255-scalar IDs, an invalid host frame after valid identity, and external-provider/non-argument enumerator failures. Public physical process consumers use actual JSONL and exclusive post-stop lease probes; native readers compare literal typed records and reject field/identity/counter corruptions for fixed reasons. Definitions do not substitute for executed evidence; results belong in the task receipt.

T03 host filtering, T04 complete ownership and T05 real factory/host shutdown qualification remain required, followed by examples/instructions/skills and release qualification. No shipping API, package, worker or general parser is added.
