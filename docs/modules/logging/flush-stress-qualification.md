# Flush stress qualification

WP05-S08-T04 qualifies the actual public FlushAsync method through internally composed Core queues and writers. It adds development tests, a shared acceptance map and an independent native report reader; it changes no shipping implementation or public API.

Each enabled destination has its own in-memory event queue and single awaited worker. These stress scenarios compose actual Core queues, workers and flush coordination through the internal CreateQueued seam with controlled MemoryStream writer callbacks. Concrete ConsoleOutputWriter/FileOutputWriter preparation is covered by earlier composition tasks; current physical result/boundary regression lanes cover file ownership and userspace visibility. Production composition prepares bounded bytes before queue admission, then its worker invokes the selected concrete writer for WriteAsync and FlushAsync. The runtime fields do not introduce a second direct output path.

The [acceptance map](../../../conformance/logging/flush-stress-cases.json) preserves all four original S08 criteria and binds them in both directions to the following actual scenarios.

| Scenario | Qualification |
| --- | --- |
| repeat-write | Hold the first write and all four distinct accepted targets; make 5,000 alternating cancelled/timed-out public calls. Each detached caller leaves zero attached continuations and at most four backing slots on its pending shared task. Four worker controls remain until their actual prefixes settle. |
| repeat-flush | Hold the initial zero-boundary writer flush, fill the three-slot queue and retain its three accepted targets. Another 5,000 calls detach without removing any of the four controls or adding another control for a repeated target. |
| repeat-progress | Seed consistent prior accounting at Int64.MaxValue - 1, admit one actual held record, then exhaust admission. Another 5,000 public waits attach to and detach from the lazy progress signal while no flush control remains. The unresolved actual record stays pending until its write confirms; failed flush confirmation cannot imply completion. |
| saturation | Race 64 producers against full console capacity while file filters their Information events. Early target 1 and later console target 4 remain distinct. Both callers time out while writers remain blocked; file retains its one control. Initial invalid/rejection facts and successful drain with earlier loss are exact. |
| cohort | Start 64 dual-output callers: cancel 32, expire 16, move 16 survivors from console to file, cancel eight there and complete eight. Inspect retained references, backing capacity, control counts and timer ownership at each phase. UTC corrections and early callbacks preserve the original overall due time. |
| failed-flush | Block both writer flushes for boundary 1, admit three later records and reject 61. Cancel 32 callers and expire 16 before console flush fails; the other 16 still await file confirmation. Later console abandonment and rejections do not enter earlier covered counts or initial facts. |
| concurrent | Race 16 producers with 64 public flush callers. Match every caller's original atomic per-output boundary and rejection facts to its immutable final result, actual accepted tickets, bytes and serialized writer order. |
| deadline-race | Exercise 32 actual deadline callbacks frozen at expiry, held inside their cancellation notification. Check linked notification remains held before releasing original-token caller cancellation or completed I/O against asynchronous disposal. The public wait remains pending until the active callback joins; its cancellation source stays alive during that join. Deadline results retain the original pending observation. |

The repeated scenarios execute 15,000 public calls per native platform: 7,500 cancellations and 7,500 timeouts. Ten sampled deadline owners per scenario (five cancelled and five timed out) become unreachable after the helper frame returns and forced collection. This is a focused retention probe, not a heap-size benchmark. The 64-caller cohort measures 64 console continuation slots before detachment, then zero retained cancelled/expired callers; file has at most 16 slots for its surviving cohort. One owned timer exists per active public caller and all timers/callbacks/joins settle by scenario exit. There is no per-caller retained output aggregate or history.

The C# fixtures make live assertions at the actual queue, callback and public API seams. Unit and process matchers additionally verify result identities, summary flags and main storage/outcome facts. The native C# parent matcher checks all reported gauges, original UTC labels/facts, producer PID, UTF-8/LF record bytes, accepted-ticket ordering and eventual diagnostics. Its 34 intentional corruptions must each fail for the exact declared reason. The current native C# flush selection includes all result, detachable coordination and fixed-boundary scenarios, physical buffered-file visibility and file ownership release. Each process has an exact runtime/PID and before/after Core/fixture identity checks; this is not one shared package qualification across lanes.

Private Task continuation/list inspection is pinned to .NET 10.0.12. Reflection on an actual internal deadline observer records the initial concurrent boundary before release without registering a new control or changing the caller's observation. These are nonshipping C# qualification mechanisms, not public memory-layout promises or future-language contracts. The exhaustion scenario has seeded logical history and one physical record; it does not claim to have written Int64.MaxValue records.

UTC corrections use a controlled TimeProvider, not operating-system clock changes. The cancellation race holds an actual Core deadline callback inside its lifetime cancellation notification; earlier T03 also qualifies an actively held system timer callback. Controlled writers perform real MemoryStream writes/flushes and expose actual held operations. They do not replace Core's queues or flushing algorithm.

Writer flush confirms userspace buffers; it does not establish fsync, power-loss durability or collector acknowledgement. S09 owns idle file-buffer interval scheduling. Public creation, bounded shutdown, provider and release qualification remain later tasks. Original supplied source plans, historical evidence and all 41 Planned release-family rows remain unchanged.
