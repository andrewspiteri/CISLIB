# Application identity discovery

WP03-S01-T01 implements actual build identity in Core's internal `CIS.Configuration` types under [Environment/Discovery](../../../implementations/csharp/src/CIS.Core/Environment/Discovery/ApplicationIdentityDiscovery.cs). The [startup contract](startup-contract.md) remains the public target. These internals are working implementation for the later resolver; the public startup facade and logging runtime are not yet implemented.

The discovery input contains an optional application assembly, application name, build version and explicit commit/build IDs. Nonblank supplied name/build values take precedence independently. Blank values are absent; selected strings are trimmed while preserving case, prerelease/build suffixes and other internal characters. Identity validation and safe aggregated configuration diagnostics remain WP03-S03; discovery must not silently clean invalid interior characters or invent a required name.

When a name or build value needs discovery, select the explicitly supplied assembly. Only if no assembly was supplied may the available entry assembly be used. A supplied assembly with unavailable metadata never switches to the entry assembly. Neither path may substitute `CIS.Core`'s assembly, including a second copy in another load context. The guard checks its library assembly name as well as the current assembly object. A complete supplied name/build needs no assembly discovery, supporting hosts with constrained assembly metadata.

The assembly name is the name fallback. Build version selects application informational version, then application assembly version, then `unknown`. It never uses file version, Core's version or a filename. `CommitId` and `BuildId` select only their explicit inputs; missing/blank values remain null, with no inference from informational suffixes or assembly metadata. An unavailable application name remains null for later configuration validation, where the selected `MissingApplicationName` issue applies.

The runtime adapter uses `Assembly.GetEntryAssembly`, `Assembly.GetName` and `AssemblyInformationalVersionAttribute`. An internal injectable reader isolates discovery from tests. Expected platform/access/I/O/attribute/type-load discovery failures are handled per read, so a failed informational attribute can still use the same application's assembly version. The explicit exception filter is in [OptionalMetadataDiscovery](../../../implementations/csharp/src/CIS.Core/Environment/Discovery/OptionalMetadataDiscovery.cs); unexpected faults and cancellation propagate. No outputs, workers, environment mutations or network calls are involved.

Forty-five native unit cases cover independent supplied values, blank/absent inputs, suffix preservation, application assembly selection, unavailable entry/explicit metadata, excluded Core identity, explicit IDs, real runtime attribute/version reading with a different file-version decoy, optional discovery failures and propagated programming faults/cancellation. Two regression cases use a real second Core assembly in a collectible load context. Three cases use collectible in-memory application assemblies with fixed distinct versions and real reflection. They are managed-runtime unit fixtures, not Windows/Linux child-process qualification or AOT/trimming support evidence.

The twelve portable metadata vectors still describe complete snapshot expectations. This task implements their application/build/explicit-ID portion; it does not execute their service-version, process/host, initialization/publication or deep-copy expectations. The broader `UT-IDENTITY` group remains Planned, while thirteen concrete `UT-APPLICATION-*` bindings require these native methods/counts. WP03-S01-T02 adds process/host/runtime facts, T03 supplies initialization seams and separation from service-version configuration, and T04 adds complete discovery/process fixtures. The Linux lane remains unexecuted.
