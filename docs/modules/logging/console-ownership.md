Console composition borrows the selected standard stream. Runtime admission closure, successful draining and terminal write failure never close or dispose it. The application retains ownership. The existing concrete ConsoleOutputWriter holds the stream and supplies WriteAsync; it has no disposal operation. One OutputEventQueue worker awaits each complete record write before starting the next, outside the admission gate. This task makes that rule explicit and qualifies the actual implementation without adding another lifetime or synchronization framework, shipping API or dependency.

Default selection remains stderr. Human/Normal is the default presentation; selecting JSONL does not change the default stream. Explicit stdout works for both formats. Options are frozen before selection as established in [console composition](console-composition.md). Serialization is per runtime/output. Unrelated application writers and distinct simultaneously running runtimes do not share this worker. Flush serialization and bounded public stop remain WP05-S08 and WP05-S10.

The [22 literal vectors](../../../conformance/logging/console-ownership-cases.json) contain eighteen controlled and four physical consumers. Controlled cases cover successful drain, a five-byte partial write followed by IOException, six concurrent producers admitting twenty-four records, idle closure and two sequential runtimes reusing the same stream. Both formats and stream selections are exercised, with default properties left unassigned. Each controlled stream holds its first record halfway through, yields between byte chunks and counts async write concurrency, synchronous/asynchronous disposal and flush calls. Once callers return, closure observes one active write, zero completed records and all accepted work pending. Releasing the writer finishes one awaited record at a time, or produces one Failed/two Abandoned and the safe WriteFailed code. No retry or runtime-owned stream disposal occurs. The application writes to both streams after completion and then explicitly disposes its selected controlled stream. Runtime tickets restart in the second sequential runtime while the borrowed stream remains usable. Cleanup releases the writer, closes admission and bounds producer/worker joins; streams are disposed in a nested finally even when joining fails, while a primary test failure is preserved.

Checks map every caller identity to its successful output ticket and compare resulting record order to those tickets. Concurrent producer scheduling does not fix the winning caller order. Full JSON facts/types, default human fields, Unicode/control escaping, records under the byte cap and complete LF records are checked against separately declared facts. Thirteen deliberate damages exercise disposal, overlap, tickets, order, payload bytes, stream routing, unresolved state, failed disposition, the held snapshot, partial-write bytes and all three declared disposition fields. Both comparers read the catalog's literal per-runtime written/failed/abandoned counts and reject each damage for its specific expected reason.

The four physical children use actual standard streams and write application JSON markers to stdout and stderr after queue completion. Parent consumers drain both streams concurrently and inspect exact-runtime/binary/input identities and an empty working directory. C# readers retain and inspect original stdout/stderr bytes, including BOM/framing, and opt into strict UTF-8 decoding. Controlled counters qualify Stream wrapper ownership and concurrency; physical bytes qualify destination selection and continued application output, without claiming instrumented concurrency inside the native standard stream.
