# File flush interval scheduling

WP05-S09-T01 adds one periodic TimeProvider timer to an enabled, fully initialized configured file runtime. CORE_LOG_FLUSH_INTERVAL_MS populates EnvironmentOptions.Logging.FlushIntervalMilliseconds; the runtime captures that value before output acquisition. Its default is 1,000 ms and supported range is 10–60,000 ms. Later mutation of the supplied options does not change the owned timer. Disabled file output allocates no interval timer.

The timer starts disarmed, is assigned to the actual file queue, then receives the captured interval as its initial due time and period. Timer creation suppresses caller ExecutionContext flow. Each callback only registers the current accepted file boundary through the existing nondroppable flush controls and wakes its worker. It does not write, flush, launch another task or await I/O. One written event followed by idle time therefore schedules another writer-buffer flush without requiring another log entry. Console has no interval timer.

The interval is a scheduling target. Worker I/O may delay completion, and userspace flush does not imply fsync, crash durability or collector acknowledgement. The existing sequential worker performs both records and flushes. This minimum request path is necessary for real T01 scheduling; timer/explicit-flush/write coalescing, blocked/continuous-traffic bounds and primitive startup races are described in [T02 qualification](file-timer-coordination.md). Configured composition starts its timer exactly once before publication; complete story qualification remains T04.

The timer is acquired after concrete console/file initialization and runtime validation, before publication. Acquisition or arming failure uses the safe file category FileFlushTimerInitializationFailed. Startup rollback closes and joins this attempt's idle workers, releases owned file handles and keeps borrowed console open. The category is an implementation refinement for the later public error catalog; preserved source catalogs remain unchanged.

Timer cleanup belongs to its owning queue. [T03 timer lifetime](file-timer-lifecycle.md) detaches and cancels scheduling at admission closure/fault, then terminal worker cleanup joins the same disposal task before releasing the file resource. Already-dispatched callbacks can finish but register no work on a closed/faulted/exiting queue. Blocked actual I/O and callback joins remain pending; the later public bounded stop/disposal operation must join this ownership. No public creation/stop placeholder or dependency is added.

[Development cases](../../../conformance/logging/file-interval-cases.json) cover three controlled idle intervals (10/1,000/60,000 ms), physical configured frozen options, a fresh-process 250 ms environment override, two disabled-file shapes, both range failures and timer creation/arming rollback. Before observing a request, each idle probe asserts that the timer has already created its actual worker control; an observation cannot inject otherwise missing timer work. Tests advance controlled time to one tick before and exactly at the due time, then await the actual registration and worker facts. The controlled idle probes also close admission while holding the queue gate and fire the still-active timer awaiting disposal before the worker can exit, requiring no new control or third writer flush. Invalid-range probes enable console so zero acquisitions proves validation precedes that acquisition. Guards bound execution; arbitrary sleeps are not the correctness evidence.

Primitive CreateQueued fixtures remain a kernel seam and explicitly opt into the same queue timer method; configured physical runtime creation starts it automatically. Controlled callbacks qualify actual write/flush counts and order. Physical fixtures use concrete FileOutputWriter and inspect actual live UTF-8 JSONL and lease/active-handle release. The active file is deliberately unbuffered, so visible bytes alone are not proof of a timer flush; resolved timer-created writer registrations establish that confirmation.

The C# matcher checks principal timer/result facts. The independent native reader additionally checks computed timer accounting, accepted targets, original producer PID, record bytes/order, worker join state and borrowed-stream state, rejecting 20 deliberate corruptions for exact reasons. Boolean fields such as beforeDue, idleNoNewEvents, optionMutationIgnored, noOutputBeforeFailure and ownershipReleased attest that fixture-internal assertions passed; their proof includes successful child execution. They are not independently measured ownership or timing facts. Native Ubuntu execution qualifies the runtime seam, not a Linux SDK or release lane.
