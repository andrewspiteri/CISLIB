# Identity validation and configuration diagnostics

WP03-S03-T02 adds internal `ConfigurationValidator` aggregation over the selected [typed resolution](configuration-resolution.md), reusing [option validation](configuration-option-validation.md). It implements the real public `CIS.Configuration.ConfigurationIssue`, `ConfigurationIssueCodes` and `CoreConfigurationException` types in CIS.Core. No startup facade or snapshot placeholder is added.

Selected ApplicationName and EnvironmentName allow at most 255 Unicode scalars. ServiceVersion, actual BuildVersion, CommitId and BuildId allow at most 512. The validator decodes UTF-16 scalars explicitly: supplementary characters count once, combining marks count separately, and isolated/reversed/interrupted surrogate pairs fail. It rejects C0/C1 control characters. It preserves case and Unicode sequences without normalization; format characters such as zero-width space/BOM are not Unicode control characters and remain permitted identity content. Selection/discovery trims surrounding whitespace first, so leading/trailing whitespace removed by that phase is not an embedded-control failure.

A selected invalid identity reports `InvalidIdentity` on its selected CORE, DD, setup or discovery source key and never falls through. Missing application identity reports `MissingApplicationName` on `CORE_SERVICE_NAME`. Explicit optional build IDs remain null after absent/blank discovery input. A valid telemetry ServiceVersion cannot hide an invalid actual BuildVersion. CommitId and BuildId are carried as copied immutable strings from application discovery into the local resolution; environment variables cannot supply them. The later public snapshot/metadata builder owns their final projection.

Independent issues follow catalog order (three selected identity settings, then logging options), followed by actual BuildVersion, CommitId, BuildId and setup EnvironmentKind. Metadata keys are `BuildVersion`, `CommitId` and `BuildId`; these are selected prepublication diagnostic labels. If an invalid BuildVersion already produced the selected inherited ServiceVersion issue with the same code/key, it is reported once. Independently selected invalid ServiceVersion and invalid actual BuildVersion remain separate problems. Known identity/option checks aggregate even for disabled outputs. Path syntax joins the same pipeline in T03; a zero-issue result currently establishes only the implemented identity/option phase, not complete valid initialization.

The issue type is sealed with getter-only strings and null argument guards. It preserves caller-supplied codes/keys/explanations, allowing future diagnostic codes; callers constructing their own issues are responsible for safe explanations. The exception constructor enumerates input once, copies in order, rejects null sequences/elements and exposes an owned `IReadOnlyList<ConfigurationIssue>` that rejects mutation. An empty sequence is allowed by this constructor, while the internal validator only throws for a nonempty result. These constructor details are prepublication implementation choices within the roadmap. Its message is fixed and its default formatting does not dump issues. Actual validation explanations exclude input strings, paths, unrelated variables and credentials; arbitrary caller-provided issue content is not sanitized or secretly rewritten.
