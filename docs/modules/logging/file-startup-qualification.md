# File startup story qualification

WP05-S05-T04 qualifies all four S05 criteria at the actual internal configured runtime and physical file boundary. The [acceptance map](../../../conformance/logging/file-startup-qualification-map.json) preserves original criterion wording and lists current native witnesses. The selected static environment/module preparation replaces the historical snapshot mechanics; no new startup abstraction is introduced.

Twenty native integration cases and Windows/Ubuntu consumers hold live runtimes in two independent processes. A same-group contender fails safely and joins its unpublished workers; the first runtime remains able to append. Two distinct live groups write records identified by the actual producing process IDs, with separately checked complete per-group order. Clean closure and forced process exit release ownership; a new process appends without changing existing inventory identity. The forced-exit case begins after a confirmed complete write and makes no torn-write/recovery claim.

A child prepares a relative Unicode path while in the origin directory, reports readiness before creating any output artifact, and then changes its own working directory before runtime creation. The parent observes no output I/O before the command, a record at the captured origin path afterwards, and an untouched later directory. Missing output directories are created only during runtime initialization. Dot-path contenders use a literal dot alias in the process command and the captured canonical path in expectations.

Both format-switch directions and missing-inventory retries preserve original active/inventory bytes. Independent literal compatible empty inventories also reject a format switch, retain metadata unchanged, and accept the matching format. Initial successful runtime groups publish persistent group IDs and UTF-8/no-BOM/LF metadata before appending, as enforced by the shipping startup order and inventory-failure probes.

Four permission cases first prove that the underlying OS operation is denied: directory creation, active-file read/write, inventory read, and lease read/write. Windows adds a narrowly selected explicit deny rule to a freshly owned temporary path and restores the exact original access ACL in finally. Inventory uses read-data denial so ACL management remains available. Ubuntu runs as an unprivileged user and restores original modes in finally. No repository or existing user-file permissions are changed. Each failure returns a safe fixed error, joins new workers, preserves existing bytes and borrowed streams, and succeeds after permission restoration. Before the failed child exits, exclusive handle probes verify lease release after active/inventory denial and both lease and active-handle release after inventory denial, missing inventory and incompatible metadata. Denied or nonexistent handles produce no affirmative probe claim; a same-group contender never acquires ownership. Successful retry then qualifies reuse after restored permissions, separately from the in-process release witness.
