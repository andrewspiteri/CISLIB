# Bounded output queue foundation

WP05-S02-T01 creates internal queues and workers. T02 now implements [internal runtime fanout and accepted tickets](queued-fanout.md); mixed output outcomes and complete story qualification follow at T03/T04. There is no new public factory or lifecycle API.

`OutputQueues` creates one `OutputEventQueue` for each enabled console/file output and none for disabled outputs. Both writer-presence checks and capacity validation happen before workers start. The internal composition caller supplies prepared capacity (1 through 65536), enabled flags and trusted writer callbacks. No mutable settings, terminal heuristics or destination creation enter this primitive.

Each bounded `Channel<AdmittedEvent>` uses `FullMode=Wait`, `SingleReader=true`, `SingleWriter=false` and `AllowSynchronousContinuations=false`. Producers call only `TryWrite` through `TryAdmit` (the primitive `TryEnqueue` delegates to it): they never await capacity, invoke a writer, perform destination I/O or create a per-entry task. A full queue returns false for incoming work and preserves its contents. At most capacity records are buffered and one is in a writer operation for each output.

One cached worker task reads in queue order and awaits each trusted callback before taking the next record. Worker creation suppresses ExecutionContext flow because the immutable event already owns producer metadata, scopes, time and trace IDs. This prevents the queue creator's Activity/AsyncLocal/culture state from becoming worker ambient state. Console and file workers progress independently. No total order between destinations or simultaneous multi-producer calls is promised.

The internal `Complete` operation closes primitive admission, is repeatable and permits successful queued work to drain. It does not implement public flush targets, stop deadlines, durability or cancellation of blocked I/O. A callback exception faults the observable worker task, closes admission and releases unattempted queue references without retry. WP05-S03 still owns safe fault diagnostics, failed/abandoned/pending counters and terminal output states; this foundation does not claim those parts complete. T02 coordinates output admission, ticket publication, dequeue and closure with the existing logger gate.

Eleven shared rows use the actual shipping Channels and controlled `MemoryStream` writers: capacities 1/2/8 with console/file/both enabled, both disabled and console progress while file is held behind a release barrier. Original bytes are saved before admission and compared with the completed stream, along with record order, queue bounds, one active callback, owned event references, closure and ambient/inline isolation. Unit tests also cover validation, maximum capacity with already suppressed flow, original synchronous/asynchronous failures, release of queued references and a joined 64-producer burst. The concurrent burst checks accepted membership, not a scheduling-dependent producer order.

The inline-execution probe offers an observation on initial admission; later admissions happen while the writer is blocked. It does not expose registration of the worker's wait or prove every scheduling race. Canonical source inspection separately verifies `AllowSynchronousContinuations=false` and one worker task at construction. The concurrency maximum uses an atomic compare/exchange loop so overlapping callbacks cannot hide a larger active count. Redundant same-property task comparisons are omitted.

Exact-runtime child processes and an independent Python comparator qualify those eleven rows on Windows and Ubuntu. These are real memory writes with controlled blocking; actual console/file streams, ownership, destinations and persistence remain later tasks. No Linux SDK, macOS, mutation qualification or release claim follows from these probes. The retained [task record](../../../planning/logging/evidence/wp05-s02-t01/receipt.json) records executed results separately from scope.
