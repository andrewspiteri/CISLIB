# Lazy capture and write outcomes

WP04-S05-T03 qualifies real CoreLogger lazy calls, global capture rejection and the output-owned results in CoreLogRuntime. Interested factories run once per write, including when admission returns QueueFull. Caller factory exceptions retain their original object and type; null returns produce InvalidFactoryResult. Captured invalid content produces one global InvalidEvent observation with a fixed safe category and no output entries or output attempts. Supported oversized content truncates, counts loss once, and can still be Accepted, PartiallyAccepted or Rejected.

[Forty-one shared descriptors](../../../conformance/logging/logger-capture-cases.json) cover null/empty/control/malformed named text, null message, invalid Unicode in template/operation ID, invalid map keys/null values/cooperative callbacks and throwing exception accessors. Existing generic attribute/exception capture errors use UnsupportedValue; this task does not promise every draft error-catalog value is emitted. Valid-invalid-valid sequences show that global capture rejection never advances either output ticket. Output admission controls start with distinct prior tickets, reject selected incoming writes and return their own next successful ticket. This checks passthrough of output-owned tickets. Contiguity is the output implementation's job; Core validates positive accepted-only tickets without maintaining a second sequence authority. Plans are admission controls. A Faulted response sets their terminal flag; later fault-state scenarios remain T04 work. The controls perform no I/O or worker delivery.

Captured records stay owned after DTO mutation. Accepted fanout receives the same EncodedEvent; queues that reject do not retain or replace earlier accepted records in the controls. Comparators inspect literal outcomes, safe codes, exact tickets/counters, factory calls for each write and in total, clock calls and original base64 bytes with strict UTF-8, cap/LF/BOM checks and selected parsed fields. Negative controls alter retry counts (including balanced extra/skipped invocations), global invalid counts, invalid-event tickets, later successful tickets, wire UTF-8, loss counts and factory-exception identity. Native children execute actual Core with exact .NET 10.0.12 and matching managed files on Windows and Ubuntu.

The only shipping change prevents invalid/truncated global counters from wrapping. A direct atomic compare/exchange increment saturates at Int64.MaxValue; that value is a lower bound once the total cannot be represented. No new metrics framework or public surface is added. Native C# tests inject near-limit/full private counters before running actual concurrent writes, and separately observe 64 writes/factories/counters and successful unique tickets. Scheduling probes do not deterministically force lost-update races; atomicity also follows from inspecting the compare/exchange algorithm. Trusted output protocol violations throw a Core InvalidOperationException without pretending they were caller-invalid capture; controls check missing/nonpositive/invented tickets and invalid statuses. A trusted protocol defect on a later output can throw after an earlier output admitted; this does not roll back that earlier admission. Output workers still own future ticket/counter limits and I/O fault handling.
