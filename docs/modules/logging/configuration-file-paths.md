# Captured directory and file-path validation

WP03-S03-T03 captures one initialization working-directory value and resolves selected file paths into local immutable validated state. [Selection/parsing](configuration-resolution.md) retains the selected raw path and provenance; `ConfigurationValidator.Validate(resolution, capturedDirectory)` requires the explicit capture, validates all selected option/identity/path settings and returns `ValidatedConfiguration.FilePath` as an absolute path or null. The later public snapshot builder must use that validated path. No public facade or output runtime is added.

`InitializationWorkingDirectory.Capture` reads its source exactly once, requires a fully qualified base and owns its normalized string. The normal source is `Directory.GetCurrentDirectory`; an internal callback qualifies deterministic inputs. Required source failures propagate rather than falling back to a later directory or inventing a configuration issue. The capture applies even when the selected file path is absent. Getters never reread the ambient directory.

Path resolution calls the two-argument [Path.GetFullPath API](https://learn.microsoft.com/en-us/dotnet/api/system.io.path.getfullpath?view=net-10.0) with the selected path and captured base. The API documents deterministic resolution independent of later current-directory changes. The selected native .NET 10.0.12 [Windows](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/IO/Path.Windows.cs) and [Unix](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/IO/Path.Unix.cs) implementations inform the policy: use native syntax rather than impose a common character/path subset. Existing directories/files, symlinks, permissions, destination ownership and writeability are not probed; runtime creation owns those checks. Core creates no directories or outputs during validation. Unicode sequences are preserved according to native path normalization.

Windows adds one lexical protection: the runtime's [PathHelper](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/IO/PathHelper.Windows.cs) expands ordinary `~` names with filesystem queries. Core replaces `~` with an unused same-width nonstructural BMP character before native normalization and restores it afterward. The marker is absent from all relevant input text; fully qualified inputs do not depend on the base. Extended/device forms that already bypass that runtime expansion retain their native handling. Marker selection first tries private-use characters, then other nonsurrogate BMP characters; exhausting all 63,230 candidates exceeds the [Windows path limit](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation). Controls preserve tilde/base/absolute text and existing marker characters, including complete exhaustion of the first candidate range. This avoids short-name expansion without changing literal user paths or probing destinations.

Absent/blank selected paths remain null. A selected path is checked even when file level is None. ArgumentException, NotSupportedException and PathTooLongException from syntactic resolution produce `InvalidPath` on the selected CORE/setup source key with fixed safe guidance; platform exception messages and raw paths are never copied into diagnostics. Other unexpected failures propagate. Windows filename/opening restrictions and Unix literal characters are distinguished from syntactic qualification: passing this phase does not attest that a destination can be opened.

The path problem joins existing independent errors at CORE_LOG_FILE_PATH's catalog position, before file format/level/numeric settings; actual build identifiers and setup kind follow afterward. The private aggregator preserves the [identity/option ordering](configuration-identity-validation.md). Explicitly named identity/option-only helpers retain component-test access, while the complete Validate method always includes path resolution once. The returned local state owns getter-only captured/absolute values and publishes no globals, workers or logging outputs.
