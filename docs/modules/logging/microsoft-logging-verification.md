# Microsoft adapter verification wiring

WP06-S03-T03 adds an explicit adapter slice to the shipping-project matrix. The shipping project, assembly and package remain CIS.Core; the slice includes all three handwritten files in Logging/MicrosoftLogger. The separate parser smoke and independently maintained module scopes remain intact. Full shipping matrix execution, source-bound disposition review and both recorded release lanes remain WP07 work.

Run from the repository root after the usual locked restore:

```powershell
pwsh -NoProfile -File implementations/csharp/eng/verify-microsoft-logging.ps1 -Mode Coverage
pwsh -NoProfile -File implementations/csharp/eng/verify-microsoft-logging.ps1 -Mode Mutation
```

Coverage runs the actual provider unit and integration projects separately through Microsoft.CodeCoverage 18.10.1 with the Core module filter and explicit child-process collection. Raw TRX attachments identify each Cobertura report. The runner writes adapter-coverage.json beside each lane report, with exact source observations and report hashes; missing or unexecuted adapter sources fail the run. Adapter source-line observations are extracted by exact source paths, including generated closures mapped to those files, rather than treating the whole Core report as sufficient adapter evidence. The execution observed 65 unit and 79 integration cases, 139/141 adapter lines in each lane. Branch observations are 91/100 unit and 89/100 integration; they remain separate observations, not an invented merged branch result. Coverage mode does not evaluate policy thresholds. The integration branch observation of 0.89 is below the declared 0.90 minimum; threshold qualification remains WP07. These are task observations, not complete release coverage certification. See [Microsoft collector configuration](https://learn.microsoft.com/en-us/visualstudio/test/customizing-code-coverage-analysis).

Mutation runs Stryker 4.16.0 on its pinned .NET 8.0.31 tool host, with net10.0 tests on 10.0.12 and Complete mutation level. It copies maintained source into a new ignored directory under the repository before building; it never instruments the shared checkout. This source copy is a disposable verification input, not a new canonical implementation. Copy hashes for all snapshot inputs are retained and rechecked after mutation. Original hashes are retained and rechecked for the three adapter sources only. Each run also records the runner, matrix, configuration and toolchain policy hashes. Failed mutation runs keep their native outputs and still verify/rebuild the unmutated copy. The configured 90% score gate is preserved. The runner rejects mismatched matrix/file sets, missing or empty adapter mutant files and a zero testable denominator, regardless of Stryker exit status. No dashboard or remote reporter is selected. See [Stryker configuration](https://stryker-mutator.io/docs/stryker-net/configuration/).

Only in-process provider unit tests currently test injected mutants. Integration children load their own ordinary Core copy; this invocation does not claim child-process mutant injection or give those tests mutation kill credit. Coverage did measure the children independently. The first complete adapter mutation invocation scored 60%, with 78 Killed, 46 Survived and 6 NoCoverage in the testable denominator 130; 23 selected CompileError and 37 selected Ignored were retained without kill credit. Whole-Core mutate-filter omissions remain outside the adapter numerator/denominator. The pre-review final run scored 55.38%: 72 Killed, 51 Survived and 7 NoCoverage, with the same denominator 130, 23 selected CompileError and 37 selected Ignored. Native per-test coverage selections and results differed between runs; both native observations are retained. The revised runner was then executed in both modes: its mutation run scored 54.62%, with 71 Killed, 51 Survived and 8 NoCoverage out of 130 testable mutants. The report guards passed, the native threshold command exited 2 and the unmutated rebuild passed. These differing native selections/results require repeatability investigation in WP07; their cause is not established here. This exposes remaining mutation/test and native-exclusion review work in WP07; it is not a passing mutation release gate or a reason to lower thresholds.

The module matrix links the actual unit/integration coverage commands and dedicated Stryker config to the same Core shipping identity. The mutation family references that matrix explicitly; fast Developer verification remains separate. No public API, shipping dependency, helper assembly or extra runtime worker is added. Original source plans and full release requirements are preserved. Candidate package compatibility, release bundle and runnable examples/activated instructions remain later tasks.
