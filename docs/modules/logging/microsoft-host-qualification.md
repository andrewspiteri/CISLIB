# Microsoft host integration qualification

WP06-S02-T05 qualifies all five original S02 acceptance criteria through actual public Core consumers and Microsoft's `LoggerFactory`/`ILogger<T>`. The application process is the host: it owns work, factory/provider registration and explicit Core shutdown. No Generic Host package, automatic `IHostedService` lifetime, ownership flag or new shipping abstraction is introduced.

Factory `BeginScope` uses the external source that Microsoft supplies through `ISupportExternalScope.SetScopeProvider`. These frames are borrowed and copied at accepted Log capture. A direct category logger created by `CoreLoggerProvider` uses the existing copied Core store instead. Two simultaneously active async operations, coordinated by ready/release barriers and yields, exercise each route. Their nested IDs and owner attributes stay separate; inner scope and event attribute overrides retain Core precedence. Mutating a scope dictionary after BeginScope distinguishes the copied direct route from the borrowed factory route. No scope leaks back into the joining caller. There is no promised global order between concurrent operations.

The typed factory case combines a direct provider-owned outer frame, factory external frames and an actual W3C Activity. Host nonblank operation IDs override the Core layer; nested host IDs win; ordinary event-state operation_id stays an attribute. A direct Core event's typed OperationId wins for that event. Free-form service/environment/version/component/resource/trace/span state stays nested and cannot replace automatic envelope facts. Default factory Activity tracking is used; the application Activity is captured by Core. Other ActivityTrackingOptions combinations are not claimed by this task.

This fixture registers with `factory.AddProvider(provider)` after factory creation. Microsoft marks that provider registration for disposal, so factory disposal calls provider Dispose. The application runtime remains alive: direct Core and another provider continue logging, and caller-owned Core scope handles stay active. This differs from passing an already-created instance into the logging builder/DI container, whose disposal responsibility stays with its owner. The fixture exercises the exact registration route; applications must follow their registration lifetime. See [Microsoft LoggerFactory source](https://source.dot.net/Microsoft.Extensions.Logging/LoggerFactory.cs.html) and [provider ownership](microsoft-provider-ownership.md).

For shutdown, the application signals its background work to finish and awaits it before calling Core StopAsync. The worker's final scoped event is admitted before closure. The owner observes the actual immutable stop result, disposes/joins the same shared operation and then disposes the factory. Repeated stop/disposal retains the same task/result and does not restart draining. Stopped logger calls skip formatting. One negative payload case has InvalidEventCount=1, a successful admitted-work drain and LossObserved=true; the owner flags that outcome for attention. Stop success alone must not hide earlier rejection. These are normal managed physical-file cases, not induced operating-system failures or power-loss guarantees; bounded stop/fault stress remains separately qualified by S10.

[Host filtering](microsoft-host-filtering.md) supplies current-assembly Debug-file/Warning-console and skipped-work regressions, including narrow-host negative cases. [Operation mapping](microsoft-provider-operation.md) supplies the typed event/nested/automatic-field cases, and [provider ownership](microsoft-provider-ownership.md) supplies lease/source-reference/caller-handle cases. The [acceptance map](../../../conformance/logging/provider-host-story-acceptance.json) preserves every original criterion's wording and binds it to concrete catalogs. Its paths and test/native execution are audited; the map itself is not execution evidence. Receipts contain exact tests, assemblies, raw records, corruption controls, review and source hashes. No source plans or release requirements are rewritten. Examples, activated instructions/skills, compatibility and full release qualification remain later roadmap work.

A supplemental factory formatter case verifies the earlier deferred boundary: direct provider formatter exceptions propagate unchanged, while Microsoft factory logging aggregates them and preserves the original exception instance. No invalid event or failed-formatter record is admitted, and later calls remain usable.
