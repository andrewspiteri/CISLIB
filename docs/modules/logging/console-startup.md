# Console startup rollback (WP05-S04-T03)

Actual console creation now checks the selected borrowed stream's CanWrite before publishing a runtime. Selector exceptions/null and throwing writability checks produce CoreLogInitializationException with fixed console/ConsoleInitializationFailed facts. An unwritable stream produces console/ConsoleStreamNotWritable. Worker acquisition errors identify the fixed console or file destination with WorkerInitializationFailed. The complete sealed exception has getter-only OutputName/ErrorCode and no public constructor; its message contains only those fixed facts, and no original exception, payload or configured path is retained. Metadata, level, byte-cap, queue-capacity and enum validation runs before console selection. Internal writer-presence validation runs before worker acquisition; a mismatched file callback still produces ArgumentException after console selection.

The concrete composition acquires its independent queues before the final console readiness check. Until runtime publication those queues are empty and no business writer callback can run. If validation or final construction fails, creation closes and joins this attempt's workers outside their admission gate before throwing. If acquisition of the second queue fails, OutputQueues also closes and joins the first. Task.Run and suppressed creator flow remain the production launcher. A small trusted internal launch delegate allows deterministic failure before task acquisition while scheduling the actual ProcessAsync worker for acquired queues; it is not a public scheduler/startup framework. Such launchers must schedule the supplied worker or throw before acquiring a task, and must not publish/enqueue startup work. Synchronous joining is safe for these idle, unpublished Task.Run workers and does not supply the later bounded public shutdown protocol.

The selected console stream is borrowed throughout selection, initialization, rollback and successful operation. None of those paths dispose or flush it. Cleanup never affects another runtime's workers. A failed attempt does not redirect to another output. Physical file handles/leases, existing file inventories and their rollback join this composition in WP05-S05; enabled file queues here still use the existing controlled writer callback.

The [36 shared cases](../../../conformance/logging/console-startup-cases.json) declare literal errors, acquisition counts, successful task joins, suppressed launch flow and every final queue fact. Thirty-two controlled cases cover throwing/null selection, real read-only and previously disposed MemoryStreams, a throwing availability getter, failure before the first/second worker starts, a pre-existing runtime, and inactive-console/disabled preparation. Four physical cases return a borrowed actual standard-input wrapper as the intentionally unwritable console seam, then check that this same wrapper remains readable and stdout/stderr still carry application markers. These failure seams use actual Core/Channel/Task/Stream behavior. They do not claim ordinary standard-input routing or physical file startup.

The fixture remembers the actual ProcessAsync target and Task.Run task returned by each successful launch. On failure, every acquired task must already be completed successfully when Create returns by throwing; every owned queue must be Stopped, empty and reject a later admission. Read-only content and prior disposed state are preserved. Another already running runtime must stay Running and accept/deliver a record after the new failure. File-only/disabled success follows normal early outcomes without selecting or checking a console. Startup getter observations are frozen immediately after the creation attempt, before real application/old-runtime MemoryStream writes can invoke CanWrite again. Ten corruption controls require specific rejection reasons for unjoined tasks, wrong worker/queue state, borrowed disposal, inherited launch flow, unsafe errors and changed stream/file bytes.

Parent processes drain both streams concurrently. Independent Python checks retain original physical stdout/stderr bytes, inspect literal task/state/error/stream facts and validate runtime/binary/input identities. The small survivor records are framed JSONL under the cap; prior capture/rendering tasks qualify size boundaries.
