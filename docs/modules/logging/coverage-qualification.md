# Shipping coverage collection

WP07-S01-T04 measures the currently implemented C# shipping code with Microsoft.CodeCoverage 18.10.1. The explicit inventory is [shipping.json](../../../implementations/csharp/verification/coverage/shipping.json): the runtime CIS.Core.dll and the packaged CIS.TypeManager.Build.dll build helper. Both count, although only Core is a runtime dependency. This collection task does not establish release qualification.

Build and pack the current candidate with `pwsh -NoProfile -File eng/verify.ps1 -Profile Developer` from the repository root (use the optional `-MaxBuildNodes 1` on hosts whose parallel MSBuild workers stall). Then run `pwsh -NoProfile -File eng/verify-shipping-coverage.ps1 -OutputRoot <new-absolute-directory>` from implementations/csharp. The latter runs every active unit, integration, architecture and business test without a filter. It returns 0 only when both assemblies and their aggregate meet 95% lines and 90% branches; 2 preserves a complete measurement that fails those thresholds. Missing reports/sources, zero assembly branch denominators, failed/skipped tests and inconsistent native counts fail collection. Mutation and cumulative compatibility are separate pending families.

The candidate archive must contain exactly the two inventoried shipping DLLs, equal to their Release outputs. Inputs, package identity, native TRX/Cobertura attachments, commands and environment are retained. Dynamic managed instrumentation collects child processes without rewriting candidate DLLs; static/native instrumentation is disabled. Two real MSBuild architecture cases exercise successful helper inventory generation and rejection of an escaping selected asset. They add no Type Manager implementation or runtime dependency.

Coverage report interpretation now runs in the existing C# checker (`ShippingCoverage.cs`), replacing `summarize-shipping-coverage.py`. For retained-report analysis, from the language root run `dotnet run --project eng/CIS.DependencyChecker/CIS.DependencyChecker.csproj -c Release -p:RestoreLockedMode=true --no-launch-profile -- shipping-coverage <matching-language-root> <new-output.json> <results-directory> [...]`. Each results directory contains its native `report.trx` and Cobertura attachment. This command evaluates the matching source project's Compile items with a finite child deadline, preserves the existing observation schema and returns 1 for invalid input, 2 for measured threshold failure, or 0 for qualified measurements. It cannot turn historical reports into current-candidate coverage; use the full collection entry above for that boundary. `ShippingCoverageTests` supplies 28 native parser/aggregation controls. See the [migration evidence](../../../planning/evidence/corrective-coverage-migration-2026-10-15.md).

The collector includes auto-properties and has no implicit or explicit source, method, attribute, company or key exclusions. Async/state-machine and other executable compiler transformations remain counted. Eleven individually inventoried enum/interface/constant-only source files have no executable sequence points, including the declaration-only `ILogWriter` interface. Their hashes and reasons remain in the inventory. Any unexpected executable source, omitted handwritten file or non-executable declaration that acquires sequence points fails validation. The source set is compared with evaluated MSBuild Compile items for each project. SDK-generated assembly metadata contains no handwritten executable body; no generated executable source is excluded from these reports.

Native class/source/line identities and branch denominators are preserved, including multiple native class entries on one physical source line. Line execution is unioned across reports. Cobertura supplies covered branch counts without stable identities for each outcome, so the summary takes the maximum covered count per line across reports. This is a conservative lower bound: complementary outcomes in separate reports receive no invented union credit. Assembly totals and the aggregate sum those counts and denominators. No OS lanes are merged. A known branching SeverityTokenParser fixture must have a nonzero measured/covered branch denominator.

The retained [task evidence](../../../planning/logging/evidence/wp07-s01-t04/verification.json) publishes per-assembly and aggregate results, source hashes, uncovered lines and partially covered branch lines. Windows collection is the current task scope. Full Ubuntu coverage, all release-family evidence and required release thresholds remain pending; earlier Linux functional results do not substitute for coverage. A helper coverage gap must be resolved with meaningful Type Manager cases, rather than removing that assembly or its difficult branches from the denominator.

Microsoft documents [collector configuration and defaults](https://github.com/microsoft/codecoverage/blob/main/docs/configuration.md) and [dynamic versus static instrumentation](https://github.com/microsoft/codecoverage/blob/main/docs/instrumentation.md). The committed settings and observed native reports identify the actual selected behavior.
