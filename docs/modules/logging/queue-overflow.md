# Incoming queue overflow and independent output results

WP05-S02-T03 qualifies the existing Core runtime and bounded Channels. No additional shipping queue, option, public API or dependency is needed: `FullMode=Wait` with nonblocking `TryWrite` already returns QueueFull for the incoming entry without evicting an older accepted slot. Complete output counters and safe diagnostics remain WP05-S03.

Capture happens once before admission. A healthy eligible output can be full while `IsEnabled` remains true; an eligible lazy factory still runs once, and valid input can then return Rejected with QueueFull and no ticket. Invalid input still produces the global InvalidEvent result with no output admissions. When no enabled output is interested (None or below every enabled threshold), the call is filtered before capture, including when queues are full. If another output is interested, capture still occurs once and the uninterested output is marked Filtered during fanout.

Results describe each enabled output independently, in console-then-file order. Disabled outputs are omitted. A full interested output returns QueueFull; an already faulted interested output returns Faulted; an uninterested output returns Filtered. At least one successful admission and one interested rejection gives PartiallyAccepted. No interested admission gives Rejected; no interested output gives Filtered. An uninterested output is not an interested rejection. Successful tickets remain positive and contiguous per output; all rejections have null tickets. An output becoming available can admit the next entry without retrying or altering a previous rejected result.

The [twelve neutral cases](../../../conformance/logging/queue-overflow-cases.json) cover each sole enabled output, both-full capacities one/two, both orientations of filtered/full and faulted/full, file progress while console is blocked, recovery of each output while its peer stays full, and None filtering during saturation. The existing T02 independent-console case supplies the opposite progress direction. Each first callback signals readiness before further producer calls, and explicit release signals control recovery. Each healthy output's final byte stream must contain exactly its accepted callers, including records held during saturation, in that output's accepted-ticket order. The controlled faulting output reports its attempted but unwritten record separately. Rejected callers cannot replace an old slot or acquire a ticket. Comparing original before/after bytes also detects mutation while held.

A fast file can finish its second record before a blocked console finishes its first. Only each destination's own admission order is promised. Observed callback progress and final per-output streams do not establish a total delivery order across destinations, concurrent callers or timestamps. Admission is not confirmed writing, persistence or collector acknowledgment.

The C# tests and exact-runtime children use the same actual-runtime fixture and complementary byte/ticket/caller matcher as T02. The independent Python runner selects an explicit T03 catalog profile, enforces its twelve named rows, additionally checks timestamp/raw framing/ticket contiguity, and rejects an eviction corruption whose replacement record and stream are internally consistent but belong to a rejected caller. C# controls separately reject eviction, missing old work and false acceptance. Producers and workers are released and joined during cleanup; there are no timing sleeps or physical destinations.

All observations use controlled MemoryStream writers and explicit original IOException faults. They do not qualify physical console/file ownership or durability, full S03 accepted/written/failed/abandoned/pending accounting, public lifecycle/provider integration or release. T04 still owns the complete story's multi-producer/bookkeeping qualification. The [task receipt](../../../planning/logging/evidence/wp05-s02-t03/receipt.json) records executed evidence and its limits.
