## Findings

### 1. [P2] An old tab can invalidate a newer, valid session and discard its unsaved work

**Location:** [`protected-context.tsx`, lines 76–78](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/components/protected-context.tsx#L76-L78), together with the [notification handlers at lines 24–27](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/components/protected-context.tsx#L24-L27).

Every local session invalidation broadcasts the same unscoped `"invalidate"` message. Every receiving tab immediately calls `owner.signOut()`, without checking whether it holds the session that became invalid.

That breaks this ordinary sequence:

1. Tab A retains an older session.
2. The user signs in again through another tab. Tab B loads the new, valid session and starts editing a Configuration.
3. Tab A reaches its old expiry, or its focus check discovers that the browser cookie now represents a different session.
4. Tab A broadcasts invalidation.
5. Tab B clears its valid context and unsaved draft.

The destructive effect is explicit: [`signOut()` clears every protected owner and the locally retained operation references](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/portal-session.ts#L93-L99). Tab B can therefore lose work even though its newer server session remains valid.

**Validation:** I reproduced the state loss using the actual `PortalSessionCoordinator` and `ProtectedStateOwner` classes with notification wiring equivalent to the provider. Expiring the older session cleared the newer tab’s draft while the newer session was still within its validity period. This was a coordinator-level reproduction, not a browser test.

**Recommended correction:** Scope invalidation to the affected nonsecret session association, or make incoming notifications trigger immediate masking followed by authoritative validation of the receiving tab’s own session. A stale document discovering that *its* session is obsolete should not automatically erase state belonging to a newer session.

**Focused regression:** Load the newer session in Tab B, create an unsaved draft, then expire or revalidate the older session in Tab A. Verify that B retains its draft and original-operation references when its own session is still valid.

### 2. [P2] An open Deploy dialog blocks the session-retry control

**Location:** [`protected-context.tsx`, lines 79–85](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/components/protected-context.tsx#L79-L85), interacting with the [native dialog lifecycle in `configuration-version-page.tsx`, lines 91–94](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/components/configuration-version-page.tsx#L91-L94).

The new session mask hides the protected document while keeping its components mounted. The Deploy confirmation uses native `dialog.showModal()`, and its effect closes the dialog only when `deploy` becomes `undefined`. Starting a session check does not clear that deployment state.

The problematic sequence is:

1. Open a Deploy confirmation.
2. Switch away from the tab and return, triggering session verification.
3. Let verification fail or time out.
4. The session notice displays **Retry session check**, but the hidden Deploy dialog still holds native modality.

The CSS hides the dialog and its backdrop, but hiding a modal does not close it. Under the HTML modal rules, controls outside the active modal remain inert—so the visible Retry button cannot receive normal pointer or keyboard interaction. This follows from the CSS top-layer rendering rules and HTML’s modal inertness rules. [drafts.csswg.org](https://drafts.csswg.org/css-position-4/?utm_source=chatgpt.com)

The [Radix `Panel` changes already suspend modality during masking](https://github.com/andrewspiteri/CISLIB/blob/857112140362006d9c1f678fc354316fa05f0021/implementations/typescript/applications/management-portal/src/components/shared.tsx#L281-L287); the native Deploy dialog needs corresponding handling.

**Validation:** This is a code- and specification-based finding. I could not run the browser reproduction in this environment. Escape may dismiss the dialog when it is idle, so I am describing a broken retry flow, not an irrecoverable page lock.

**Recommended correction:** Close or suspend the native modal while verification is checking or unavailable. Preserve the deployment selection and note in component state, and restore the dialog only after successful validation of the same session.

**Focused regression:** Open Deploy, force a failed focus check, and verify that Retry works by both pointer and keyboard. A successful retry should restore the selection and note without issuing a deployment.
