## 1. P1 — The Configuration list fails at 15 entries

Simply opening the Configuration tab for an application with **15 or more Configuration entries** can throw:

> The protected portal owner limit was reached.

Each row mounts `ConfigurationRowActions`, which calls `usePortalRead` even when its menu is closed. Passing `null` prevents the HTTP request, but the hook still registers a protected-state owner. The session coordinator permits only **16 owners**, and the application page already uses two for its application and list reads. The fifteenth row therefore attempts to register owner 17. The list request defaults to 100 rows, so this is well within the normal supported page size. [Row action component](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/components/configuration-list.tsx#L28-L47) · [Unconditional reader registration](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/components/shared.tsx#L26-L38) · [Owner limit](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/portal-session.ts#L41-L47)

**Impact:** An application with a modest Configuration inventory cannot reliably open its Configuration tab or reach pagination. No action menu needs to be opened to trigger this.

**Verification:** I reproduced the registration failure using the actual coordinator and protected-state classes: two parent readers plus 14 row readers succeeded; registering row 15 threw the error. The connection to the rendered list is confirmed by the component code. I did not run that scenario in a live browser.

**Correction:** Create the action reader only while a row’s menu is open, or use one shared reader for the selected row. Keep a meaningful owner limit.

**Focused regression:** Display at least 20 Configuration entries, open and close several row menus, and verify that the page remains usable and retired readers are released.

## 2. P2 — Signing out in one tab leaves protected content visible in other tabs

The protected-state coordinator belongs to one browser document. Signing out clears that document’s state, but there is no cross-tab invalidation mechanism. When another tab regains focus, its handler only checks the expiry timestamp it previously captured; it does not check whether the shared session cookie has been removed or replaced. [Focus and sign-out handling](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/components/protected-context.tsx#L10-L44) · [Local expiry checks](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/portal-session.ts#L90-L110)

The affected sequence is:

1. Open two portal tabs as operator A.
2. Display protected Configuration JSON or an unsaved draft in the first tab.
3. Sign out in the second tab, optionally signing in as another operator.
4. Return to the first tab before its previously recorded expiry.

The first tab continues displaying operator A’s protected content until expiry or another API interaction detects the changed session. This conflicts with the requirement to clear protected client state on sign-out and user switching. [RM-09 security requirement](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/planning/management/portal/sources/CISLIB_RM09_Management_Portal_Specification_v1.0.md#L117-L123)

**Impact:** Protected values and drafts remain visible after sign-out. The server’s context checks still protect subsequent commands; I did **not** find a corresponding authorization bypass.

**Correction:** Broadcast session invalidation to other same-origin tabs and revalidate the session when a tab becomes active before retaining its protected display. The notification needs no credentials or protected values.

**Focused regression:** Use two tabs in the same browser context and verify that signing out or switching operator clears the other tab’s rendered Configuration values and draft.

This finding is established by the lifecycle code; the two-tab browser scenario was not executed during this review.

## 3. P2 — Refresh does not refresh an open Configuration editor

The page’s **Refresh** button increments the parent’s revision. That refreshes the saved-version list, assignment map, action permissions and selected-version content. However, the revision is not passed to `ConfigurationVersionEditor`, which owns a separate revision for its `/editor` request. [Page Refresh and editor wiring](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/components/configuration-version-page.tsx#L181-L202) · [Editor’s independent revision](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/components/configuration-version-editor.tsx#L33-L51)

This causes two practical failures:

- **After a transient editor-read failure:** the editor tells the operator to refresh, but clicking the page’s Refresh button never retries `/editor`.
- **After another operator changes the source or deployment:** the page refreshes its map, while the open editor retains its previous source and assignment ETags. Save continues submitting those old preconditions to candidate preview, which correctly rejects them. [Save’s captured preconditions and preview command](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/configuration-version-commands.ts#L43-L73)

Because the second failure happens before publication, there is no completed operation reference to dismiss through the recovery path that happens to refresh the child editor. The normal escape is to cancel and reopen the editor or reload the page, discarding the in-memory draft.

**Correction:** Connect the page’s refresh revision to the editor’s protected read, preserving the current draft while refreshing the source, assignment and permissions. Changing the React key would remount the editor and lose the draft.

**Focused regression:** Open a draft, change the source or assignment through another operator, click Refresh, and verify that the editor rereads its context, retains the draft, and saves using fresh preconditions. Also verify recovery from one failed `/editor` read.

## 4. P2 — The service CI job selects portal tests without preparing the portal

The workflow installs the TypeScript workspace and runs:

- `build`
- `test`
- `check:browser`

Those are the portable SDK commands. The portal has a separate `build:portal` command, which the workflow does not run. Nevertheless, the subsequent .NET test filter selects the portal host integration tests. [Workflow preparation and selection](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/.github/workflows/service-tests.yml#L48-L110) · [Separate workspace commands](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/package.json#L17-L22)

This revision makes portal startup verify that its pinned Next response-close correction has already been prepared. Following the workflow’s preparation sequence on a fresh install leaves that correction unapplied and the production `.next` build absent. [Startup guard](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/src/server/next-response-drain.ts#L48-L58)

**Verification:** After the clean dependency installation and portable build, I invoked the actual startup guard. It failed with:

> Build the portal to prepare its pinned Next response-close correction.

The later explicit portal build succeeded.

There is also a browser prerequisite to address: the version workflow launches **headed Microsoft Edge**, while the Ubuntu CI job does not provision a display for that test. [Browser launch](https://github.com/andrewspiteri/CISLIB/blob/87d18ba65b0d7a34c7b9f93bea5134a90a1b5b34/implementations/typescript/applications/management-portal/tests/native-browser-checks.mjs#L10-L17)

**Correction:** Build the portal and provision the selected browser/display before running these integration cases, or move them into a dedicated, fully provisioned portal job.

**History qualification:** The missing portal-build setup already existed in the parent revision. This commit adds the mandatory startup guard and headed version scenario, making the preparation gap directly relevant to its new tests.

## What looks sound

The main Configuration design is implemented with the intended separation:

- **Save** publishes the Application JSON and creates an immutable release.
- **Deploy** makes the separate assignment decision.
- Editing an older version preserves its exact Shared reference.
- Commands retain their original keys before dispatch, and uncertain outcomes use original-result recovery.
- Central authorization checks remain authoritative; browser action hints do not grant permission.
