# HC05 pipe and matching probe implementation

This is an implementation handoff, not an executed verification receipt. The coordinator owns project/manifest integration and all native build/test execution for the combined candidate.

`HealthPipeServer` is inert until `StartAsync`. It uses exactly `PipeMaxClients` reusable accepting/connected slots, with one actual handler per slot and no task-per-waiting-client queue. Each connected slot has one total request/response deadline, measured by the supplied `TimeProvider`, including explicit elapsed-time checks around synchronous snapshot/format work. Report serialization consumes one detached snapshot and the HC03 codec supplies framing, strict request validation and complete bounded responses. Transport errors never alter monitor health.

After writing one frame, a slot asynchronously waits for client closure, unexpected extra input or that same deadline before disconnecting. The matched client closes after reading its complete response. This preserves unread Windows pipe data without an uncancelable synchronous drain: [`DisconnectNamedPipe`](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe) discards unread buffered bytes, and successful `WriteAsync` only proves the write completed into the pipe. No additional protocol acknowledgment or retry is introduced.

Ordinary accept/disconnect I/O errors recreate only the affected fixed slot. A client can close before acceptance is observed; this must not terminally stop unrelated reporters. One asynchronous endpoint-change semaphore serializes the fixed workers' removal/recreation operations, so there is no additional client task queue, no temporary excess beyond `PipeMaxClients`, and the last endpoint is reclaimed with first-instance protection. Genuine replacement-creation or security errors still close admission terminally. A replacement opened while stop races is disposed before that actual worker leaves the shared drain.

Stop is terminal: it closes admission, cancels and disposes accepting/connected streams, then waits for every actual worker and any in-flight startup resource creation to settle. Cancellation of a caller's wait does not release a handler slot. A synchronous application snapshot source cannot be forcibly aborted; it remains accounted until it actually returns. Timer and elapsed-time checks prevent it from committing a successful reply after its request deadline.

The nonpackable `CisHealthProbe` executable calls internal Core `HealthProbeClient` through an explicit friend assembly. It accepts only the four C08 options, uses local server `.` and `CurrentUserOnly`, and shares the exact HC03 strict response parser instead of duplicating the schema. Connect, request write and response read share one total monotonic deadline, without an application retry. A complete validated selected snapshot goes to stdout and returns 0 or 1 for the selected result. Argument, transport, protocol, report and deadline failures return 2 with bounded static stderr codes. The current development invocation is `dotnet CisHealthProbe.dll`; a distributable `cis-health-probe` command/package remains a separate packaging action.

The coordinator accepted the minimal Windows native endpoint factory because the pinned [.NET 10.0.12 Windows named-pipe source](https://raw.githubusercontent.com/dotnet/runtime/v10.0.12/src/libraries/System.IO.Pipes/src/System/IO/Pipes/NamedPipeServerStream.Windows.cs) implements `CurrentUserOnly` with an owner-only ACL but creates the pipe without `PIPE_REJECT_REMOTE_CLIENTS`. The factory uses a protected owner-only ACL matching that owner boundary, noninheritable handles, first-instance name protection, asynchronous byte mode and [`PIPE_REJECT_REMOTE_CLIENTS`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipew). It wraps the resulting safe handle in the standard asynchronous BCL pipe stream; no runtime dependency or public API was added. Unix uses the normal BCL `CurrentUserOnly` constructor, whose pinned implementation checks peer effective UID after accept.

Actual ACL/endpoint behavior and exact runtime/platform belong in the native test receipt. Source inspection proves the selected flags, not an executed remote-host denial. No Linux endpoint execution or Linux permission qualification is claimed by this handoff. A supported Windows/Linux release still requires the corresponding real platform lane and exact-package qualification.
