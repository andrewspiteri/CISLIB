# HC00 concrete surface supplement

Revision 0.2, unpublished. The [catalog](contract-catalog.md) supplies semantics; source hashes in `baseline.json` identify exact declarations. This supplement records shapes left unspecified in the v0.1 attachment, rather than leaving individual workers to infer them.

* `HealthApplicationIdentity` uses required named-init `Name` and `InstanceId`. Explicit identities must have a nonempty UUID and nonblank name; future service validation uses scalar bounds Name 255, BuildVersion/ServiceVersion 512, HostName 255 and OsDescription 1024. The service's omitted identity is copied from existing `EnvironmentOptions`; it is not another global store.
* Text limits count Unicode scalar values. Caller-supplied malformed UTF-16 is rejected. Free diagnostic messages are truncated at 1024 scalars; structural code/type identifiers above their bounds are rejected. Runtime exception projection replaces malformed surrogates, bounds text, retains no exception, and marks `IsTruncated` when replacement/truncation or an inaccessible overridden message requires omission. No arbitrary exception graph or stack is projected.
* `HealthDiagnostic` has an optional-argument `(code, message, exceptionType)` constructor and `FromException(exception, code, message)`. `HealthMeasurement` has `Unavailable`, `String`, `Boolean`, `Integer`, and `Number` factories, each requiring the key and actual observation time. Unit defaults null, IsDiagnostic defaults true. Factory timestamps are normalized to UTC; string/boolean/Int64/double storage is exposed by distinct nullable getters. Unavailable has no scalar, and a numeric zero is an actual measurement.
* Public snapshot properties remain getter-only. Internal named construction inputs avoid long positional constructors. Collection arrays are copied into owned read-only storage. State coordination remains responsible for coherent values, registration/metric ordering, policy interpretation and limits; DTO construction is not a second state engine.
* When a policy has an outcome object, Failed increments its consecutive failure streak and Succeeded resets it; skips and expected cancellation are neutral. Only the ConsecutiveFailures policy uses that streak to classify health. Availability records refresh-failure streaks diagnostically while preserving published usable-data availability.
* `HealthCollectionResult` provides the catalog factories, a public `Kind`, optional policy scalar getters and owned `Measurements`. `WithMeasurements` replaces its previous optional measurements and requires a health-bearing result. Diagnostics-only collection uses `Diagnostics`. Lists are copied, bounded to 32, keyed ordinally, and reject null entries, duplicate keys and `IsDiagnostic=false`.
* `HealthCollectionAttempt.EvaluationFailed` identifies an unexpected/malformed evaluation, not an ordinary valid negative health result. A valid breached numeric condition, flagged condition or failed execution remains a committed policy observation. TimeProvider hooks, like other supplied code, run outside the state gate. State coordination still orders accepted commits, not inferred wall-clock causality.
* `HealthCollectionAttempt` exposes disposition, evaluation-failure flag and optional diagnostic. Exactly one collector attaches to a live local monitor. Internal `RegisterCollection`, `TryReserve`, `TryEnter`, `CommitResult`, `CommitEvaluationFailure`, `Complete` and `WithdrawCollection` are concrete interfaces. Reservation identities support joining one runner-owned task. Health/per-key revisions use `BigInteger`; generation uses nonnegative Int64 with checked advancement and retirement before exhaustion, never wrapping or reusing an identity. Completion includes lease acquisition/cleanup disposition without inventing a callback outcome. Capacity remains with the runner through actual settlement. Internal withdrawal returns the shared settlement task and signals cancellation outside the state gate.
* Execution input facts use required RegistrationId, Kind and OccurredAtUtc plus nullable positive Int64 ExecutionId for execution-scoped facts. Registration-lifetime facts omit ExecutionId. Exact phases, statuses, timing fields and detached diagnostics are in the C# input/snapshot types. The wire ExecutionId is a canonical positive Int64 decimal string, preserving precision like counters. Durations ending `Milliseconds` in memory become `...Ms` on the wire.
* The binding keeps current/previous records and a high-water mark. The internal state seam atomically binds, applies one deduplicated outcome, updates lifecycle and releases association. `ReleaseBinding` returns the shared actual-settlement Task. A state-issued reporting handle can retain the created monitor while the caller owns the binding; the registry must never retain the binding/owner graph. A contradictory retained terminal fact is `InvalidOperationException` with a bounded safe explanation; malformed arguments use argument errors. Neither is a second callback failure.
* `IHealthStateAccess` connects the real Core service/factory and monitor handles to stable `CollectionState` and `ExecutionState` identities. Binder overloads require this internal access or reject the supplied monitor/factory with an argument error before any state change. Factory binding calls the atomic state operation directly, never public Create followed by Bind. The runner captures its service's CollectionState and requires reference equality with the monitor's CollectionState before registration; state then rechecks liveness/stopping/attachment atomically. Access is read outside the gate; the registry retains no access object or caller-owned monitor graph.
* `HealthReportBuffer.Utf8Bytes` is owned read-only UTF-8 memory; IsError, ErrorCode and SelectedHealthy expose the formatter result. Formatter/pipe/server/service/runner/binder/HTTP installation signatures are currently checked by a nonshipping facade only. `HealthPipeServer.StartAsync(CancellationToken waitCancellation = default)` makes the previously unspecified start-cancellation shape explicit.
* Schemas use local URN identifiers and no network resolution. JSON Schema handles structural rules; the actual HC03 reader must enforce duplicate property rejection at every depth, a maximum depth of 16, complete count/list consistency, readiness and selected-view semantics, UTF-8, framing and budgets. Authored fixtures are not transport execution evidence.

The original acceptance wording is preserved. HC-AT-57's assembly-wide independence from ASP.NET is superseded by HC-D01; policy/state implementation remains independent of HTTP/DI types and Heartbeat. Core must still reject unapproved dependencies. All other local/external acceptance obligations remain.
