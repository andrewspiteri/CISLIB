## 1. Purpose and delivery outcome

RM10 supplies a durable trigger and Scheduled Task layer around the existing CISLIB Jobs runtime. A module owns and registers a trigger. Central Management owns the built-in calendar provider; other services can register callback, message and custom sources. A trigger fires and registers an event. An enabled Scheduled Task associates that event with one application-registered job and supplies the resource and invocation input. An eligible instance of the owning application executes the admitted run under its verified workload identity.

The module also supplies durable run and attempt history, configuration descriptors, management operations and portal integration. The main configuration object presented to operators is **Scheduled Task**, with its association settings above exactly two contextual tabs: **Trigger** and **Job**. Both tabs follow the task's selected identities. History is a separate view or action.

Completion means that real calendar and application-produced events can queue the correct jobs, survive source and worker interruptions, execute with the required ownership and permissions, and produce accurate recoverable history. Multiple management and application instances must preserve the same authoritative event, run and original-operation identities. A retry must not repeat an already committed business effect where the selected durable-operation and effect-protection contracts apply.

The requirements below settle the product behaviour discussed with Andrew Spiteri. Numeric limits and the operational defaults table are explicit first-release decisions made in this specification. No further product question blocks planning. The accepted editor remains the governing design; uncovered visual work follows the limited approval boundary defined below.

**MUST** and **MUST NOT** identify requirements. **SHOULD** permits a documented implementation choice that preserves the required outcome. **MAY** identifies an optional capability. Public API names describe required concepts where an equivalent API is already published; implementation must reuse those APIs rather than create competing owners.

## 2. Required delivery scope

| Area | Required first release |
| --- | --- |

| Scheduled Tasks | One configured trigger to one registered job, with explicit target resource, typed input mapping, immutable revisions and current enablement. Several tasks can share a trigger or job. |
| Admission and execution | Atomic bounded event-to-task fan-out, durable pending runs, compatibility and authorization checks, existing Jobs dispatch, ownership and original-operation recovery. |
| Configuration and UI | Owner-described forms, RM08 publication/adoption, the accepted task-centred editor, coherent preview and guarded activation. |
| Identity | Application workload execution, separate requester/producer/executor attribution and honest supported-profile selection. |
| Versions and deployments | Actual worker build recorded per attempt, captured job execution contract, graceful drain and explicitly compatible recovery across upgrades or rollback. |
| History | Central durable run/attempt records, bounded progress and summaries, separate task/job reporting views, retention and safe result access. |
| Persistence and clients | One production PostgreSQL integration using the existing Management product backend, additive portable contracts, C# and TypeScript management clients. |
| Qualification | Focused managed tests, existing real-provider integration fixtures, consumer documentation, native UI checks and CIS traceability. |

A general cron language, arbitrary workflow dependencies, an expression language, a universal webhook gateway, user-delegated execution, a new broker, a general Audit archive and an independently hosted worker fleet are outside this first release. Other shared-store technologies may implement the same required semantics later; implementing Redis and Cosmos DB adapters is not part of RM10 completion. Existing continuous jobs retain the RM05 lifecycle.

## 3. Existing foundations and integration rules

The specification extends the current published boundaries. The prior [RM05 implementation specification](https://github.com/andrewspiteri/CISLIB/blob/2a0fc9e07e0c9f66aa0a65026662d2d63d9a4b0c/planning/coordination/sources/CISLIB_RM05_Shared_Coordination_Specification_v1.0.md) establishes the Jobs integration and leaves production recurrence to this module. The linked module contracts are the implementation reconciliation sources. They are not a claim that RM10 already exists or has passed native qualification.

| Existing module | Required responsibility |
| --- | --- |
| RM01 Security | Native credentials, trusted caller scopes, capability checks and actual effective policy. |
| RM02 Transactions | Application-owned original transaction and Committed, NotCommitted and Unknown completion evidence. |
| RM03 Operations | Stable original operation references, duplicate protection and original-result recovery. |
| RM04 Messaging | Existing message contracts, codecs, inbox/outbox and reliable transport where selected. |
| RM05 Coordination and Jobs | Handler eligibility, resource exclusivity, leases, fencing, invocation capacity, dispatch and continuous iterations. |
| RM06 Audit | Attributable administrative and business records through its existing durable delivery integration. |
| RM07 Management | Authenticated registration, lifecycle, authoritative control and finite new-work admission. |
| RM08 Configuration | Trusted definitions, coherent publications/releases/assignments and actual owner adoption. |
| RM09 Portal | Existing application shell, supported controls, UI design process and typed management integration. |
| Core services | Existing CISApplication startup, Heartbeat, Configuration, Type Manager, Logging, Metrics, Healthcheck and CommonTesting. |

**RM10-INT-01 Compatibility and dependencies.** Target .NET 10 and preserve the repository's dependency policy and published compatibility commitments. Reuse existing approved PostgreSQL, Messaging and test-provider arrangements. Add no external runtime dependency to portable/Core contracts and no third-party scheduling framework. Existing unmanaged Jobs use and unrelated application startup must remain unchanged when RM10 is not selected.

**RM10-INT-02 Persistence authority.** Central Management remains a CISLIB consumer and owns its scheduler store, schema migration and transaction completion. The initial production provider extends its existing PostgreSQL backend. It MUST support atomic event receipts and run creation, guarded revision changes, unique identities, due-state arbitration, authorized outcome recording and quota accounting across replicas. A process-local store or lock cannot satisfy production durability or multi-instance correctness. Keep the provider contract portable without implementing additional storage products speculatively.

**RM10-INT-03 Startup and lifetime.** Construction and registration remain passive. Reuse sequential startup for credentials, catalog validation, configuration adoption and provider activation. A managed application cannot start a trigger producer or job invocation before its required live bootstrap and reconciliation. Management's own calendar lifecycle must not introduce a circular requirement to bootstrap the Management authority through itself. Shutdown stops new admission, drains actual owned work and reporting/outbox responsibility, then disposes dependencies in the existing order. Reuse bounded background-work facilities; keep coordination renewal independent of business execution capacity.

**RM10-INT-04 Production delivery integration.** Deliver a concrete production adapter from authoritative pending runs to the existing application Jobs dispatcher, in addition to the programmatic and RM04 event-ingress adapters. Use existing transport and bounded source reconciliation facilities. A transport notification may be acknowledged only when authoritative durable responsibility remains recoverable. Startup, reconnect and interruption recovery MUST rediscover unfinished work without depending on a lost in-memory wakeup. Do not hold a Messaging inbox transaction open for the full duration of an arbitrary job callback. The durable handoff and application transaction boundaries must be documented and proven with the selected provider.

**RM10-INT-05 Execution admission ordering.** Central task enablement, pending-run cancellation and permission to start an attempt MUST have a defined authoritative serialization point. A disable/cancel decision that wins before attempt admission prevents that attempt. An attempt admitted earlier remains subject to the existing runtime entry checks, managed admission, lease and cooperative cancellation rules; the portal must not describe disablement as an instantaneous physical stop. Publish the concrete boundary and test both race orders. No second lease system may replace RM05 ownership.

**RM10-INT-06 Portable representation.** Use existing exact, ordinal, case-sensitive identifiers and unambiguous structured keys. Validate finite UTF-8 limits before retention. Schema versions, revisions, generations and sequences use lossless decimal strings at JSON boundaries where the existing contracts require them. Instants are UTC with explicit source time-zone metadata where applicable; durations use declared units. Reuse the existing MessageContract, codec and Command envelope for admitted job input. Publish exact field limits and validation behaviour in the checked-in wire contracts; do not expose CLR types, delegates or bearer credentials.

## 4. Core model and ownership

**RM10-CORE-01 Trigger ownership.** A trigger is registered and implemented by its owning module or application. Central Management registers and owns the built-in calendar provider. Other applications can register callback, message or custom providers. Registration declares identity, supported configuration and emitted event contracts; it grants no execution permission by itself. Provider construction and registration remain passive. The existing sequential startup owner starts an enabled provider only after its required configuration, credentials and runtime prerequisites are ready.

**RM10-CORE-02 Definitions and configured triggers.** A provider definition describes a supported source type. A configured trigger identifies one named source using a supported definition and immutable configuration revision. The calendar provider supports multiple named configured triggers. Other providers explicitly declare whether additional configurations may be created. An application may expose a fixed source without offering arbitrary instance creation. Replicas advertise support for the same logical definitions; process registration must not create duplicate trigger identities or replace their schemas.

**RM10-CORE-03 Application registered jobs.** Applications register the executable job definitions and their exact handler bindings. The portal selects those definitions; it cannot invent handlers, upload executable code or choose an arbitrary CLR type. A job declares its execution scope, stable JobId, supported modes, resource contract, required execution capabilities, input contract and supported settings. Categories retain their existing organizational and local policy role. Sharing a category does not make one application eligible to execute another application's job.

**RM10-CORE-04 Scheduled Task.** Scheduled Task is the public name of the association previously called Link. One task has one stable TaskId and references one configured trigger, one registered job, one resource-resolution rule and one input mapping. It also has a name, enablement and immutable revisions. Several tasks may reference the same trigger or job. Changing its settings creates a desired revision while preserving TaskId. That revision becomes active only after required validation and adoption; the previous active revision remains authoritative until promotion or explicit disablement. Activation does not require every replica to adopt simultaneously. A task creates at most one run for each accepted source event; application-owned batch processing remains inside the job.

**RM10-CORE-05 Events, runs and attempts.** A trigger event records one source occurrence. A task run is one logical execution admitted for one task and resolved resource. An execution attempt is a particular effort to execute or recover that run. A source event can produce several independent runs through different tasks. Each run has its own original RM-03 business-operation reference. Redelivery, retry and takeover preserve RunId, original operation reference and accepted input; they create no replacement logical run. Task revision and attempt identity are execution evidence, not ways to bypass duplicate detection.

**RM10-CORE-06 Existing execution contract.** RM-10 supplies trigger production, authoritative event admission and durable run ownership at the source boundary. It uses the existing `IJobRunSource`, `IScheduledJobDispatcher` and `JobRuntime` integration for application execution. Existing `ExternalOccurrences` compositions remain supported. Event-triggered activation must work without a fabricated calendar descriptor; adapt capability validation compatibly. Job/resource ownership remains `(Environment, ExecutionScope, JobId, ResourceId)`; task, trigger, event, occurrence, category, revision and process identifiers are outside that key. Existing job-attached calendar registrations receive a compatibility adapter that creates the equivalent trigger/task relationship without changing their published timing or identity semantics. [Existing contract](https://github.com/andrewspiteri/CISLIB/blob/main/contracts/coordination/jobs.md).

## 5. Provider and mapping contracts

**RM10-CORE-07 Portable registration.** Trigger, job and task contracts are bounded portable data with explicit versions and exact identities. Runtime type objects, delegates, native claims and credential material remain within the owning process. Trusted catalog provisioning establishes immutable definitions; authenticated application registration advertises supported definitions and versions within its permitted scope. A conflicting declaration under an existing identity/version is rejected. An unavailable owner can remain visible as registered metadata, but discovery alone cannot activate it or establish compatibility with an execution.

**RM10-CORE-08 Callback and custom sources.** The initial implementation provides a programmatic trigger-event submission port and an adapter to the existing RM-04 message-consumption/delivery path. Application callbacks and custom providers use that common port. A webhook-specific adapter may validate its external protocol and translate it into the same event, but a generic public webhook gateway is not required. A condition-checking provider defines whether a firing represents an edge, a level or a distinct source occurrence; it must preserve that occurrence's identity across submission retries.

**RM10-CORE-09 Source responsibility.** A producer creates and retains its original event identity before an uncertain submission can occur. It uses an existing durable source/outbox or another declared recoverable source when loss-free delivery is required. RM-10 must not acknowledge responsibility based only on an in-memory notification. Retrying a submission uses the original event identity and unchanged semantic content. Existing Messaging owns its transport, retry and outbox lifecycle; RM-10 adds no broker, inbox framework or independent message-delivery engine.

**RM10-CORE-10 Input mapping.** A task maps accepted event fields and configured constants into the registered job input and exactly one validated resource. The initial mapping model supports exact compatible fields, constants and bounded deterministic registered transformations, including an explicit calendar-instant-to-local-date transformation. An enabled mapper must have a trusted implementation available to the authoritative admission adapter. Mapping performs no network call, arbitrary script execution or dynamic consumer-type loading. Unsupported application-specific transformations stay in application logic until an appropriate trusted mapper is installed. Required fields, conversions, mapper version and complete output size are validated before admission commits.

## 6. Calendar production

**RM10-CORE-11 Required schedule forms.** The central calendar provider implements the existing FixedDelay, Daily and Weekly descriptors. Daily and Weekly require an explicit supported IANA time zone and local time; Weekly requires a nonempty distinct weekday set. Metadata inspection remains possible while disabled. Enabled activation validates actual zone availability and the complete supported policy. All admitted instants are recorded in UTC, with the intended local schedule context retained for explanation. The portal's next-occurrence preview uses this same evaluator. [Existing descriptor semantics](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/jobs.md).

**RM10-CORE-12 Calendar boundaries.** A nonexistent local time is skipped. A repeated local time fires once at the earlier instant. For one configured trigger, the same intended scheduled instant has one canonical event identity even if several management replicas evaluate it. Recording the event, its derived task runs and the corresponding calendar progress is one atomic durable admission. A process crash must not advance progress while losing its event, or create a second event by re-evaluating an already committed instant. Merely changing a configuration revision does not make a previously emitted instant new.

**RM10-CORE-13 Schedule changes.** An adopted active schedule change records an effective boundary. Publishing a desired change alone cannot alter production. Newly enabled or changed Daily/Weekly schedules start with matching instants strictly after that boundary; they do not backfill periods in which that configuration was not active. Existing admitted events and runs retain their original versions. Unemitted old-revision Daily/Weekly backlog is superseded at the boundary and reported compactly; it is not reinterpreted using the new schedule. A pause and resume without changing a Daily/Weekly schedule retains its cursor and applies its missed-event policy. FixedDelay retains its predecessor and single successor as specified below. Server authority determines due-state transitions; local wakeups do not authorize them.

**RM10-CORE-14 Missed events.** Every Daily/Weekly configuration explicitly stores Skip, RunLatestOnce or CatchUpBounded. RunLatestOnce is the initial editor/default profile: resume produces only the latest eligible missed instant and advances past older missed instants. Skip advances to the next future instant. CatchUpBounded emits a bounded batch of outstanding instants in chronological order within its configured window, preserving the cursor for remaining eligible backlog. Instants outside that window are skipped with a compact reason/count. The count bounds one production batch, not permission to drop eligible durable pending work. Already admitted pending runs are unaffected by missed-event calculation. These policies do not apply to FixedDelay: an overdue FixedDelay successor remains one pending cycle and cannot be skipped away or expanded into catch-up cycles.

**RM10-CORE-15 Fixed delay.** FixedDelay is measured from the shared, established completion time of the preceding logical run, including its allowed retries. Its configured trigger must designate exactly one Scheduled Task before enablement; associations with another TaskId are rejected. This avoids an implicit multi-job completion barrier. The first event is due one configured delay after initial enablement by default; an explicit StartImmediately option can select the enablement boundary. Completion feedback is accepted only for the exact predecessor run. Manual runs or unrelated job completions cannot advance this trigger. While the designated task is disabled, retired, no longer associated or lacks a valid active revision, the producer retains the pending cycle and does not register a zero-run event. When that task becomes eligible, at most the one due successor is admitted; worker unavailability alone does not prevent durable admission. A delay edit preserves the predecessor and applies only to the next unadmitted firing using its established completion or initial/resume boundary. It never replaces an accepted event or run.

**RM10-CORE-16 Fixed delay failure and recovery.** A predecessor with an established successful job outcome, including recovered original success, schedules its successor after the configured delay. The default pauses the FixedDelay trigger after a known terminal failure or cancellation, recording the reason; an explicit Continue policy for those terminal outcomes may instead schedule the successor from that terminal completion. Explicitly resuming a trigger paused by a known terminal failure or cancellation starts its next delay at the recorded resume boundary; this is distinct from retrying the failed run. An indeterminate outcome is not terminal and never advances the trigger. Restart, retry and takeover recover the same predecessor and next-due record. Re-enabling with an unresolved predecessor resumes its recovery; it cannot discard the predecessor and start a fresh cycle. Closing admission or temporarily pausing a healthy cycle preserves its single successor rather than creating elapsed-interval occurrences.

**RM10-CORE-17 Bounded producer ownership.** Central Management hosts calendar production through its existing application lifecycle and bounded background-work facilities. Shared durable arbitration makes production safe across replicas. Renewal and business execution limits retain their existing owners. The implementation must not create a thread per trigger, an unbounded queue of ticks or a permanent record for each poll. No application instance independently becomes a second built-in calendar producer merely because it executes a calendar-triggered job.

## 7. Durable event admission

**RM10-CORE-18 Event identity and provenance.** Event identity is scoped by the installed authority, authoritative environment, registered trigger and original source event identity. The owner/producer is established from native authentication and trusted registration. Producer claims, instance labels and payload actor fields are recorded according to their trust contract and do not establish authority. Immutable semantic content includes the trigger/version, original occurrence time, optional scheduled instant, event contract, correlation/causation facts and exact bounded payload. Transport attempt identifiers and the server's received timestamp are separate observations.

**RM10-CORE-19 Duplicate admission.** Admission checks the original event identity before resolving a new task set. Identical replay recovers the original durable receipt and originally selected runs, including after configuration changes; response disclosure follows CORE24. Conflicting semantic content under that identity is rejected without replacing history. The source must not use a new identity because a response was lost or a result lookup was inconclusive. The store retains sufficient duplicate-protection state for the declared delivery/replay lifetime; pruning display history cannot permit a previously accepted event to create new work.

**RM10-CORE-20 Atomic bounded fan-out.** For a new event, one management-owned transaction validates the source and captures each enabled matching task's coherent active revision/configuration capsule, registered mapper versions, resolved targets, original operation references and immutable input bytes. It creates every selected run, stages required delivery intent through the existing outbox and records the event receipt together. A bounded fan-out limit is checked before committing effects. Invalid selected mappings or capacity refusal fail the whole new admission with a structured reason; partial fan-out is not reported as acceptance. No independent distributed transaction spans Management and application databases.

**RM10-CORE-21 Selection time.** A source event is associated with the authoritative active task set at its first successful registration, not by trusting its claimed historical occurrence time. An event produced offline but first accepted after an active configuration change therefore uses the current active task set. Its original occurrence time remains visible. An already accepted event reuses its original set on every redelivery. Adding, editing or removing a task cannot cause duplicate registration of an old event to create another target run. A separate deliberate historical replay feature is outside the initial scope.

**RM10-CORE-22 Eligibility and waiting.** A selected task must be enabled, structurally compatible and authorized for its exact trigger, job and resource. No currently available application instance is required merely to record otherwise valid pending work. Local job/category disablement, unavailable instances, unsupported deployed versions or capacity limits become dispatch waiting reasons; they do not erase the accepted occurrence. An event with no enabled matching tasks may be durably accepted with zero runs and an explicit receipt. Redelivery of that accepted event remains a zero-run result.

**RM10-CORE-23 Immutable execution settings.** A run pins the task revision, trigger/event contract, mapper version, job input and execution/recovery contracts, and effective execution/business configuration selected at acceptance. The application receives a detached validated per-run settings view through its execution context or typed adapter. A handler must not accidentally substitute a later mutable `IConfigurationObject` value for captured run settings. This adds no second live Configuration root and changes no existing singleton/remap rule. An instance unable to support the pinned contracts/settings must defer or refuse according to a defined outcome, never silently reinterpret them. Actual worker build provenance and compatible replacement rules are defined by VER01–09.

**RM10-CORE-24 Receipt and uncertainty.** A successful submission receipt means the complete event and selected pending runs are durably committed. It does not mean a job started or completed. A known rejection, known noncommit and indeterminate commit remain distinguishable. Recovery uses the original identity and authorized receipt lookup. The internal receipt retains the complete selected run set; a producer's response may confirm acceptance without disclosing target identities, counts or run details for which that producer lacks read permission. Redaction never changes the underlying selection or duplicate protection. An absent observation alone does not prove a timed-out mutation cannot still commit. Late source callbacks cannot create new identities, extend authority or overwrite a successor's state.

**RM10-CORE-25 Delivery and replay.** The scheduler source retains authoritative pending work until its defined disposition. RM-04 delivers notifications or commands using existing transport mechanisms; duplicates are expected to resolve to the same occurrence. A notification is a prompt to dispatch, not self-authenticating permission. Where durable outgoing intent has already committed, its delivery remains valid under existing Messaging rules. Event production or callback ingress must not be exempted from the selected host's managed-admission rules. An unavailable authority cannot be replaced by cached configuration and an invented acceptance receipt.

The operator action **Run task now** uses a trusted task-specific manual event/admission targeting exactly that ScheduledTaskId and its active revision. It checks current permissions, enablement and input compatibility and uses the ordinary durable occurrence path. Its receipt and original request identity prevent duplicate manual runs. It neither fires the shared configured trigger nor queues other tasks associated with that trigger. Disabled tasks refuse new manual execution; the command provides no force-execution bypass. A future **Fire trigger** command, if supplied, must be a separate explicitly authorized fan-out operation.

## 8. Application execution and recovery

**RM10-CORE-26 Dispatch boundary.** A run is converted to the existing admitted-occurrence contract with the same exact target, input, original operation identity and captured execution settings. The selected source validates this complete immutable admission. Jobs performs its existing local enablement, scope preparation, authorization, capacity reservation, ownership acquisition and callback-entry checks. New handler invocation remains gated by RM-07. Busy and Deferred retain source responsibility and update a bounded waiting reason; they are not business failures or permission to create a replacement occurrence. [Existing dispatcher boundary](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/scheduled.md).

**RM10-CORE-27 Exclusivity across tasks.** All tasks and trigger kinds targeting the same environment/scope/job/resource contend on the existing RM-05 key. A manual request, another trigger or a new task revision does not bypass that boundary. Different resources may execute in parallel within the existing local limits. Event deduplication prevents duplicate delivery of one source event; distinct events remain distinct requests. If several requests represent the same business action, the application must use an explicit business idempotency identity or a declared bounded coalescing policy. General cross-event coalescing is not implicit in v1.

**RM10-CORE-28 Ownership and protected effects.** RM-05 owns acquisition, renewal, generation, loss, draining and exact-grant release. Correctness-sensitive database effects use its guard in the original RM-02 transaction; remote effects require their supported recipient-enforced protection or original operation contract. Lease loss, timeout or requested cancellation cannot prove rollback or physical handler termination. No scheduler guarantee states that paused former code cannot resume. Local occupancy and capacity stay charged until the existing runtime's actual callback/scope settlement, and cleanup retains its dependency ordering.

**RM10-CORE-29 Completion and uncertainty.** Completed and PreviouslyCompleted preserve established original business completion. Prepared or staged effects are not completed work. Indeterminate transaction or delivery results remain unresolved until original-operation recovery establishes their disposition. A reported failure without sufficient completion evidence is not proof that effects can be repeated. Recovery attempts use current valid authority while retaining the original operation identity. Confirmed outgoing intent and established committed results remain valid after the originating lease ends; later cleanup diagnostics are recorded separately.

**RM10-CORE-30 Retry classes.** The default permits no automatic replay of a failed business callback. An explicit task/job retry policy may allow a finite number of further business attempts only through the original idempotency/recovery contract and the declared safe-failure classification. Known pre-execution deferral or known noncommitted dispatch failure can be rescheduled without consuming a business-attempt allowance. Recovery of uncertainty is distinct from replaying business work. Unauthorized, unsupported or invalid-contract results require a relevant state change or operator action and must not enter an aggressive retry loop.

**RM10-CORE-31 Retry timing.** The initial dispatch/recovery waiting profile begins at five seconds and backs off to a sixty-second ceiling with bounded jitter. Existing local RM-05 acquisition retry ownership is preserved; RM-10 does not nest a second immediate acquisition loop around it. When automatic business retry is explicitly enabled, the initial profile permits at most three total business attempts, including the first, and uses the same bounded delay range. Next-attempt time is persisted once per admitted retry decision. Identity, input and accepted configuration remain unchanged. Operator retry uses the existing run and original operation; a deliberately new execution is a separately named action with new provenance.

**RM10-CORE-32 Continuous duties.** Existing continuous jobs retain their finite-iteration handler contract, lease ownership, idle waiting and fault behaviour. Every new iteration passes current managed admission. Trigger/task dispatch targets a handler mode that supports a finite admitted invocation. It must not create another indefinite continuous callback for each incoming event. An application needing event-assisted continuous processing may explicitly expose a finite handler that records work for its continuous duty. The continuous duty's business checkpoint and operation identities remain application-owned.

## 9. Worker versions and deployment compatibility

A run retains the job semantics it was admitted to perform. Each attempt separately records the actual worker code used to execute or recover it. Deploying a new application release does not rewrite either fact. The default is to drain an old worker and let its entered finite work settle within the existing shutdown budget; interruption uses the ordinary original-operation recovery path.

### Version identities

| Identity | Meaning and capture point |
| --- | --- |
| Application release version | Human-readable deployed release, using the existing Management application-version metadata; copied into each attempt. |
| Immutable build identity | Exact deployable artifact, such as an image digest or immutable build identifier that resolves to the actual build; copied into each attempt. A mutable image tag or release label alone is insufficient. Source commit and deployment identifier may supplement it. |
| Job implementation identity | Exact handler implementation used by the attempt. It may reference the application artifact when the handler ships in that artifact; a separately versioned handler retains its own artifact identity. |
| Job execution contract version | Version of the trusted registered job definition covering admitted semantics and supported execution/recovery behaviour, in addition to input, settings and result contracts. Reuse an existing definition version that expresses this boundary; a second compatibility registry is unnecessary. Pinned in the task revision and logical run. |
| Checkpoint contract version, when supported | Version of application-owned durable continuation state. Captured with the checkpoint and its original run/operation; absent for jobs that do not support checkpoint continuation. |

**RM10-VER-01 Actual build provenance.** An RM10-enabled job MUST provide bounded application/build and handler implementation metadata from the selected worker's immutable startup/handler registration. Copy that metadata into the durable attempt-admission record before effect-producing callback entry, while preserving the distinction between admission and observed entry. The worker MUST validate that the selected local handler matches its registration. Versions MUST NOT be taken from event payloads or replaced by the deployment's current desired version. Authentication establishes who reported the metadata; this does not introduce binary attestation. Unavailable historical provenance MUST remain explicitly unknown rather than inferred from the current fleet. Existing application-version reporting is reused and extended compatibly; it is not by itself an exact artifact identifier.

**RM10-VER-02 Run and attempt history.** Every meaningful execution or recovery attempt MUST retain its own immutable build/implementation identities. One run may therefore show execution by build A followed by recovery or continuation by build B. Preserve the build responsible for the original business outcome when established; a new build that only reads an already committed result MUST NOT be credited with executing its effects. Display unknown original provenance explicitly if the evidence is insufficient. Run summaries may derive first and latest attempt versions, but MUST NOT overwrite the individual records or compress a mixed-version run into a single misleading worker version. Existing retention and capacity limits apply; no binary archive is stored in scheduler history.

**RM10-VER-03 Explicit compatibility.** The owning application MUST declare the exact job execution-contract versions each registered handler can start and recover, including the corresponding input, captured-settings, operation/result and optional checkpoint contracts. Reuse versioned trusted job definitions and instance capability observations. A newly admitted run pins its selected execution contract alongside its existing immutable capsule. A worker may serve that run only through an explicitly supported binding. Matching job names, JSON shape, application release numbers or a newer semantic-version label do not establish recovery compatibility. The minimum default accepts exact declared contract matches; support for earlier contracts must be explicit. A legacy adapter without an independent compatibility declaration may derive an opaque contract identity from its exact known handler build, permitting that build without inventing cross-build compatibility. Existing unmanaged Jobs consumers remain unchanged.

**RM10-VER-04 Mixed-version eligibility.** Dispatch MUST check the actual worker's supported contracts and current admission/draining state, and revalidate compatibility before callback entry. A compatible new build may execute a queued or interrupted old run while honouring its captured contracts; the run is not automatically retargeted to the new job semantics. If no eligible compatible worker exists, preserve pending or unknown responsibility with a bounded `NoCompatibleWorkerVersion` reason. This is not a business failure and does not consume business retries. Authorized read-only original-result recovery may still resolve a run where supported, even when no worker can continue its business execution. Version changes never add a component to the RM05 job/resource ownership key. During a rolling deployment, old and new builds contend on the same key; deployment ordering does not provide a second ownership mechanism.

### Draining and interrupted execution

**RM10-VER-05 Planned deployment.** Reuse the existing worker/host drain lifecycle. Draining MUST close local entry to new runs, retries, acquisitions and continuous iterations, with corresponding eligibility observations in Management. A stale control-plane observation cannot override the local drain gate. Already entered finite callbacks may finish under their captured code/settings and valid ownership within the existing finite drain budget; required lease renewal and durable outcome delivery retain their existing lifetime. In-flight handler code or its implementation identity MUST NOT be hot-swapped. A continuous duty finishes its entered finite iteration or reaches its supported safe boundary, then relinquishes ownership after actual settlement. New workers pass normal authenticated bootstrap and compatibility checks. An old worker must not release protection early simply to accelerate rollout while its callback can still produce effects.

**RM10-VER-06 Forced interruption and takeover.** A shutdown deadline, forced termination or crash initiates interruption handling; it does not by itself establish logical failure, business cancellation or rollback. A deadline may only request cancellation while the callback remains live: retain local occupancy and dependency lifetime until actual callback/scope settlement, and do not fabricate a settled-at observation. Recover the original RunId, RM03 operation reference and accepted capsule. Establish any original committed result before considering continuation. A replacement needs the existing valid RM05 grant for new protected effects and must pass the version checks above. Ordinary retry classification, limits and authorization still apply; deployment is not independent permission to replay a business callback. Unknown remains unknown until evidence resolves it. Fencing and recipient protection remain necessary because loss of ownership does not prove the former code physically stopped. Changes to the deployment version or attempt identifier cannot create a fresh business operation.

**RM10-VER-07 Optional checkpoint continuation.** RM10 MUST NOT claim to resume an arbitrary method at the interrupted instruction. A job that supports continuation MUST declare its versioned application-owned checkpoint and safe-boundary contract. Checkpoints identify the exact run/original operation, committed progress and state format. Where business progress and its checkpoint share the application's database, commit them together in the protected original RM02 unit for that step; other effects require the application's existing idempotency/reconciliation guarantees. Resumed processing preserves the logical run and the original identities of previously attempted business units. Checkpoint writes must not advertise uncommitted work as completed, and a stale owner cannot advance continuation state. A newer build serving an old contract MUST preserve its required semantics and supported state format. No automatic state migration or generic workflow/checkpoint engine is added. Without such a contract, recovery is limited to the job's declared original-result recovery and safe replay capability, or retains an unresolved disposition.

**RM10-VER-08 Deployment and rollback guidance.** The consumer guidance MUST explain how to mark workers draining before replacement and align the existing application/lease drain budget with the host or orchestrator's termination budget. Report remaining active and unresolved runs by required contract and observed build so deployment tooling can determine the effect of removing a version. Do not promise that an external deployment system will wait indefinitely. Keep the database, operation, checkpoint and settings formats required by old workers/runs usable for the intended overlap and recovery period. Rollback has the same compatibility checks as upgrade: an older build cannot consume a newer run or checkpoint merely because it is being restored. If support disappears, expose the retained blocked/unknown work until a compatible worker or explicit application-owned resolution is available. RM10 supplies these observations and gates, not a deployment orchestrator or automatic schema-migration system.

**RM10-VER-09 UI and focused qualification.** The Job tab MUST show the selected execution contract and authorized worker-version compatibility information; it remains part of the existing two-tab editor. History MUST show each attempt's application release, exact build/handler identity, execution/recovery role and version-related waiting reason. A version change between attempts and missing original provenance must be visible. Use bounded authorized filters and pages; build identifiers must not become unbounded metric labels. Qualification MUST exercise both graceful completion on the old build and interrupted recovery on a compatible new build, rejection of an incompatible worker, original-outcome provenance, continuous-duty drain and rollback against unsupported state. Reuse existing native fixtures and a focused consumer example.

The existing [scheduled execution lifecycle](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/scheduled.md) already closes admission during drain, preserves entered finite callbacks within their lease drain budget and retains original operation identities. These requirements add explicit build attribution and cross-version eligibility. Platform guidance must also account for [host shutdown callbacks being unavailable after an unexpected process failure](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services?view=aspnetcore-10.0#stopasync) and [container termination grace periods](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#termination-of-pods).

## 10. Enablement and lifecycle

**RM10-CORE-33 Trigger pause.** Pausing a calendar trigger stops new emission and retains its schedule cursor. Resuming unchanged Daily/Weekly configuration applies the missed-event policy; FixedDelay resumes its retained predecessor/successor state under CORE15–16. Pausing an external trigger closes new admission for that configured source with a retryable TriggerPaused outcome; it does not acknowledge and discard the producer's event. Identical replay of an event accepted before the pause may still recover its existing receipt. A source adapter retains or releases its upstream responsibility according to its existing reliable-delivery contract.

**RM10-CORE-34 Task pause.** Disabling a task stops new events from associating runs with it. Runs already pending for that task remain durable and do not begin a new effect-producing attempt until the task is re-enabled or those runs are explicitly cancelled. Already entered callbacks may settle under their captured settings and independent authority. Enabling the task affects future new events and resumes eligible retained runs; it does not retrospectively attach runs to events that were accepted while the task was disabled. Re-enablement preserves every retained run's original revision and operation identity.

**RM10-CORE-35 Job pause and retirement.** Disabling a job uses the existing job/category/host gates and defers all affected tasks' pending runs. It does not mutate their accepted identities. A task may be retired to prevent new associations while preserving history and unresolved work. Physical deletion is allowed only under the retention policy after protected references and unresolved responsibility are absent. Cancelling pending work is an explicit state transition; requesting cancellation of active work remains cooperative and is not immediate proof of a terminal result.

**RM10-CORE-36 Management outages and restart.** While managed admission is closed, no new scheduled attempt, retry, acquisition or continuous iteration enters business execution. An entered finite callback retains the existing settlement rules, and valid ownership may continue renewing where the current contract permits. Restarted application instances require live authenticated bootstrap and reconciliation. Recovery first reconciles authoritative state and original unresolved outcomes, then resumes eligible pending work. The portal's availability is independent of those backend gates. [Managed admission](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/managed-admission.md).

## 11. Initial operational defaults

These are implementation defaults selected by this specification; they are not claims that each numeric choice was separately approved during brainstorming. Deployments may choose stricter bounded values through supported configuration.

| Setting | Initial value or policy |
| --- | --- |
| New configured trigger and Scheduled Task | Disabled until explicitly enabled |
| Daily and Weekly missed-event policy | RunLatestOnce, explicitly stored |
| CatchUpBounded default when selected | 100 instants per batch, seven-day look-back window |
| Maximum tasks selected for one event | 64, with whole-admission refusal if exceeded |
| FixedDelay first occurrence | One configured delay after enablement; StartImmediately is explicit |
| FixedDelay terminal failure/cancellation | Pause; continuation requires an explicit setting |
| Automatic business callback retry | Disabled |
| Opt-in retry profile | Three total business attempts; delay starts at five seconds and caps at sixty seconds |
| Busy or management/capacity deferral | Preserve the same pending run and use bounded waiting |
| Pending-run expiry | No automatic expiry in the initial profile; explicit cancellation and queue limits control responsibility |
| Continuous iteration history | No permanent row for every idle iteration or heartbeat |
| Planned worker deployment | Drain the old instance within its existing finite budget; let entered work settle on its original code |
| Replacement worker eligibility | Explicit support for the run's captured execution/recovery contract; no inference from a newer release label |

**RM10-CORE-37 Finite capacity.** Payload, decoded input, fan-out, pending runs, concurrent admissions and retained reporting state all have explicit finite limits. An implementation must reserve enough capacity for the complete intended admission before accepting responsibility. At a configured storage or pending-work limit it returns a structured capacity refusal; it never drops accepted pending work to admit new events. Limits must account for the whole fan-out and existing Messaging/Configuration bounds, not only each individual payload. The final module limits table defines the numerical storage and wire profile shared by APIs and tests.

**RM10-CORE-38 Compatibility and implementation restraint.** Existing callers, job bindings, coordination key semantics, provider ownership and Configuration behaviour remain compatible. Additive adapters supply the new trigger/task model. The implementation uses the existing .NET 10 lifecycle, security, transaction, operation, Messaging, Configuration, Audit, logging, metrics and testing facilities. A full cron language, arbitrary workflow graph, unbounded event replay, universal webhook gateway and independently hosted execution fleet are outside the initial scope. A supported extension must not claim these capabilities until its complete contract is implemented and validated.

## 12. Execution identity and authorization

### Workload execution

**RM10-ID-01 Application identity.** The required execution mode is the target application's established workload identity. Calendar production, callback receipt and manual invocation do not substitute the trigger producer, task editor or browser user for that identity. Each attempt MUST establish the actual native authentication evidence through the existing RM-01 host integration and open the independent execution scope already owned by RM-05. A deserialized caller object, event field or configured display name MUST NOT establish authority. This preserves the current [scheduled execution boundary](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/scheduled.md).

**RM10-ID-02 Separate identities.** Records MUST distinguish `ConfiguredBy`, `TriggerProducer`, optional `RequestedBy`, `ExecutedAs` and the reported execution instance. `ConfiguredBy` belongs to the captured task revision. `TriggerProducer` comes from authenticated event ingress or its validated retained provenance. `RequestedBy` identifies an established manual requester or trusted upstream request origin; an automatic calendar event has no invented human requester. `ExecutedAs` contains the actual principal and selected profile established for the attempt. Instance labels remain operational metadata and MUST NOT be represented as independently verified replica identity. Issuer-qualified stable subjects are authoritative; display names are diagnostic.

**RM10-ID-03 Current authorization.** Before ownership acquisition and again in the execution scope before callback entry, the runtime MUST authorize the registered job's complete required capabilities against the actual environment, execution scope and resolved resource. Use the instance's effective Security policy and the selected provider's credential-validity rules. A queued occurrence does not confer indefinite execution permission. Refusal MUST preserve pending responsibility or produce a defined terminal rejection according to the source's disposition policy, without entering the business handler. Management admission, local enablement and RM-05 ownership remain independent requirements.

**RM10-ID-04 Permission to request work.** Management MUST authorize creation, modification, activation, manual execution and cancellation against the actual Scheduled Task and its source/target resources. It MUST validate that the permitted source-to-task-to-job association and input mapping cannot address resources outside the approved scope. Authorization to emit an event alone does not permit arbitrary job selection. Worker authorization is checked separately from the operator's or source's permission to request work. Resource values derived from event input require validation by the registered resolver before protected effects.

### Profiles and policy changes

**RM10-ID-05 Execution profile selection.** A task MUST reference an approved execution profile supported by the selected application/job; the default is the application's normal workload profile. When only that profile is supported, the editor displays the identity as inherited and read-only. An alternative workload profile MAY be selected only when the host has a real native credential and enforcement path for it and the operator has permission to use it. Profile identifiers, identity claims or reduced capability lists MUST NOT impersonate another principal or claim to attenuate a more privileged credential. This release does not require provisioning separate credentials for every job.

**RM10-ID-06 Credentials and captured intent.** Task definitions and queued runs contain profile references, never passwords, private keys, browser tokens or renewable credentials. Each admitted run MUST also retain the expected canonical workload identity or an immutable approved identity-binding version, so a mutable profile alias cannot redefine its execution intent. Each attempt obtains current valid native evidence for that captured binding. Normal credential rotation and current policy revalidation may preserve the same canonical principal. Changing a task's execution profile creates a new task revision for future admissions; recovery of an older occurrence MUST NOT silently substitute a different principal. Remapping an existing profile alias to a different identity leaves old runs blocked or refused until their captured identity can be supported; it does not rewrite their intent. Missing support or authority leaves the run blocked with a safe reason. Actual downstream authentication and applicable database access MUST enforce the selected execution boundary.

**RM10-ID-07 Policy adoption.** Security policy versions used by attempts MUST be recorded as safe metadata. RM-01 currently captures trust, profile, identity mapping and grant policy in an immutable startup snapshot; adopting changes requires restart or replacement of affected instances. The portal MUST distinguish publication from effective adoption and MUST NOT promise instantaneous revocation or hot switching that the selected provider does not implement. Existing permission checks remain authoritative under their actual effective policy. See the [Security policy and scope contract](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/security/README.md).

**RM10-ID-08 User attribution and delegation.** A manually requested run normally retains the operator as `RequestedBy` and executes as the workload. An organization-owned recurring task does not depend on its creator retaining a browser session; governance changes act through task and authorization policy. Genuine user-delegated execution is outside the initial implementation. Unsupported execution modes MUST be refused during activation and MUST never fall back to a broader workload identity. A business authorization such as a customer mandate remains an application-owned, validated business record; recording its reference does not fabricate identity-provider delegation. The application determines and rechecks that mandate's validity for each business action.

## 13. Execution history and reporting

### Durable run and attempt records

**RM10-HIST-01 History owner.** Central Management MUST persist scheduler run and attempt history in its selected authoritative scheduler store. The application remains authoritative for its business operation's outcome. The existing Jobs observations are bounded cached telemetry and explicitly retain no event queue or history; RM-10 MUST add durable records through the new scheduler boundary rather than infer history from logs or metric scrapes. Reuse existing observers where suitable. See [Jobs observations](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/coordination/observability.md).

**RM10-HIST-02 Logical run identity.** Each admitted Scheduled Task occurrence has one stable run identity and original RM-03 operation reference. Retry, redelivery, ownership transfer and recovery preserve those identities and add distinct attempts where execution or a meaningful recovery action actually occurs. Ordinary polling, Busy observations, renewal and capacity deferral MUST NOT each create an execution-attempt row. One trigger event can create several independent task runs. Task history and aggregate job history MUST query these same records, without duplicating them into unrelated histories.

**RM10-HIST-03 Run contents.** A run MUST retain its trigger/event identity, Scheduled Task identity and captured revision, exact job/application/environment/resource, original operation reference, correlation information, selected execution-profile reference, queued time, intended scheduled time when present, first admitted start, final outcome time when known, outcome/reason, and attempt count. Immutable configuration/input references, versions and digests identify the admitted execution capsule. History MUST NOT duplicate complete payloads merely to populate its list view. Protected runs pin the data required for their actual execution and recovery; later history can explicitly report that expired optional detail is unavailable.

**RM10-HIST-04 Attempt contents.** An attempt MUST identify its run, attempt identity, actual execution principal/profile, effective Security policy version, reported application instance, actual application release and immutable build/handler identities under VER01–02, relevant ownership/acquisition identity, start and settlement observations, duration where established, outcome and safe diagnostics. Business completion and callback/scope cleanup are separate facts. Configured actor, request origin and executor fields MUST remain separate. Durations SHOULD come from the executing owner's monotonic timing; happened-at and received-at timestamps MUST remain distinguishable so delayed reporting and clock differences do not manufacture an exact cross-host duration.

### Outcomes and reconciliation

**RM10-HIST-05 Run states.** The logical state model MUST distinguish `Pending`, `Running`, `RetryPending`, `Succeeded`, `Failed`, `Cancelled` and `OutcomeUnknown`. Waiting conditions carry bounded reason codes, including closed management admission, no eligible instance, missing authority, occupied resource and exhausted local capacity. They are not business failures. `Succeeded` requires established job completion; `Failed` requires a defined terminal job failure. Preserve original transaction completion separately. An unknown commit MUST NOT become a known failure or success merely because a callback threw or a response deadline expired.

**RM10-HIST-06 Cancellation and loss.** A cancellation request, elapsed timeout, missing progress report or lost lease MUST NOT establish that code stopped or that effects rolled back. A run can become `Cancelled` before execution when authoritative cancellation wins admission, or after execution only when the actual settlement and business outcome justify that disposition. Known committed success remains success with separate timeout, loss or cleanup observations where relevant. Ownership loss can end an attempt's authority while the logical run remains recoverable. The portal MUST show stale observations as stale, with the last known state and its age.

**RM10-HIST-07 Recovery.** An uncertain run MUST retain the original operation identity until established recovery determines its outcome or the defined operational disposition leaves it unresolved. Recovery restores the original recorded logical outcome and business result, with a recovery indication; it does not claim a second business execution. `Succeeded` is recorded only when the recovered job outcome establishes success. A durably recorded business failure or cancellation remains that outcome. Callback failures and retry policy MUST preserve the existing RM-02 `Committed`, `NotCommitted` and `Unknown` distinctions. No reporting failure, missing history row or expired optional history payload authorizes a new-key replay. The application's recovery capability and evidence limits determine what can be established.

**RM10-HIST-08 Report admission.** Every report MUST be authenticated and authorized for its actual application, run and attempt. Retained provenance on an RM-04 retry route must be validated through the existing transport contract; arbitrary payload identities grant no authority. Reports carry an attempt-scoped monotonic sequence and immutable identity. Identical redelivery is idempotent; conflicting content for the same sequence is rejected. Lower or stale progress cannot overwrite newer authoritative state. Sequences use the existing exact portable integer representation and exhaustion refuses further mutation rather than wrapping.

**RM10-HIST-09 Late outcome evidence.** A previous owner's late report MUST NOT restore ownership or authorize new effects. Valid original completion evidence may nevertheless resolve the same run's unknown outcome after the originating lease ends. Management MUST append or retain that reconciliation fact and preserve the earlier attempt history. It MUST not discard a proven original commit solely because a newer attempt or loss observation exists. Only the designated application/result authority may establish that business outcome; reported success labels from unrelated instances are insufficient.

### Delivery and business summaries

**RM10-HIST-10 Durable completion path.** Each production job integration MUST identify how an original outcome remains recoverable: existing durable operation/checkpoint state, a committed outcome notification through RM-04, or both. Where supported, stage an outcome notification in the application's original RM-02 transaction beside its business effect and operation result. A staged message is not proof of commit. Management receipt and the application transaction are separate milestones; the implementation MUST NOT claim atomic commitment across their independent databases. If a crash leaves no sufficient durable outcome evidence, retain `OutcomeUnknown` and refuse unsafe automatic replay.

**RM10-HIST-11 Outage settlement.** Already admitted work MUST be able to settle under its existing independent authority without waiting for synchronous Management progress I/O. Committed outcome notifications remain deliverable through the existing outbox after Management recovers, including when new-work admission is closed. Final callback cleanup may be observed separately from business commitment. Reporting MUST reuse the existing delivery/lifetime infrastructure and MUST NOT introduce an unbounded private queue, second retry engine or blocking dependency on the portal.

**RM10-HIST-12 Progress bounds.** Progress is optional, bounded telemetry. Retain the latest observation and meaningful milestones, coalescing intermediate updates. The initial publication limit is one ordinary progress update per attempt per five seconds; material state changes and terminal reports use their own reliable path and MUST NOT be dropped by progress coalescing. Unknown totals remain unknown. Continuous duties retain their existing execution lifecycle; history records meaningful ownership sessions, checkpoints, failures and aggregate progress rather than one permanent row per short iteration, idle poll or heartbeat.

**RM10-HIST-13 Result summary contract.** A job MAY register a portable typed result-summary contract and authorized detail-reference contract. The summary describes business results such as examined/processed counts, findings and an optional report reference. Its schema and content are validated and bounded; the initial summary limit is 16 KiB of encoded JSON within the selected enclosing message/body limit. A producer must omit or explicitly reject unsupported detail, not truncate it into a misleading result. Larger reports stay with their designated owner. A result count or finding does not independently decide success: the registered job outcome contract does.

**RM10-HIST-14 Read access.** History reads, filters, totals, pagination and report-detail access MUST authorize the actual application/environment/resource. Event submission and receipt recovery do not grant permission to inspect every target run. Acceptance may be confirmed without revealing unauthorized run identities, target names, counts or details. An operator's permission to see status does not automatically disclose inputs, result payloads or linked documents. Sensitive fields are omitted or redacted under the declared contract; safe error codes replace unfiltered exception/request bodies in central history. Detail references require their own authorized resolution. The portal MUST distinguish recorded facts from current freshness and display the identities and configuration revision captured for the selected run.

### Retention and audit

**RM10-HIST-15 Retention defaults.** Initial policy retains completed detailed run/attempt history for 30 days after confirmed terminal disposition and daily aggregate statistics for 180 days. These are specification defaults, configurable within explicit finite limits. Pending, running, retryable, unresolved and unsettled responsibility MUST NOT be deleted by age-based history cleanup. Finite quotas MUST refuse new admission before protected responsibility or settlement records are lost. Capacity planning MUST reserve bounded headroom for the completion and recovery of work already admitted; telemetry history has no priority over that responsibility.

**RM10-HIST-16 Duplicate protection.** Readable-history retention is independent from compact event/task admission receipts and original-operation duplicate protection. Source replay validity MUST be explicit and finite. Receipt retention MUST cover all permitted event replay, source redelivery, pending-run and retry/recovery horizons, together with the existing RM-03 protection requirements. Reject an inconsistent shorter policy. If a safe replay cutoff cannot be established, retain compact receipts and apply finite quota/backpressure. Reuse existing provider/operation policies where suitable. Pruning history MUST NOT make an earlier event or operation appear new. After compaction, an expired request must still receive an explicit stale/expired disposition; cleanup MUST NOT erase unresolved responsibility merely to admit new work.

**RM10-HIST-17 Audit boundary.** Configuration changes, activation decisions, manual execution requests, execution-profile changes and cancellation requests MUST produce the required RM-06 administrative audit facts through its existing delivery path. Application-required business audit remains in its original transaction policy. History and Audit correlate through stable references but have different persistence responsibilities. RM-10 MUST NOT add a general audit archive or assume that an emitted audit message has reached one. This follows the existing [Audit persistence boundary](https://github.com/andrewspiteri/CISLIB/blob/main/docs/modules/audit/README.md).

**RM10-HIST-18 Reporting views.** The Scheduled Task exposes History as a separate view/action; its accepted configuration editor retains its two contextual Trigger and Job tabs. The primary history row represents one logical run and expands to attempts. Job history aggregates those same runs across tasks. Trigger-event detail identifies resulting runs or a bounded reason that no run was admitted. Reports and aggregate success/failure counts MUST state whether they count logical runs or attempts; recovery attempts must not inflate completed business-operation counts. Required native verification covers duplicate/out-of-order reporting, commit acknowledgement loss, takeover, stale observation, result authorization and protected cleanup using existing provider fixtures.

## 14. Configuration contracts and registration

**RM10-UI-01 Owner supplied descriptions.** A trigger or job owner MUST register a portable, versioned description of the configuration it supports. The description MUST identify the logical owner, execution scope, stable definition identity, display name, category where applicable, configuration definition and schema version, and supported management operations. A trigger MUST declare its emitted event contract. A job MUST declare its invocation input contract and MAY declare a bounded result summary contract. These descriptions supplement the execution registrations; they do not instantiate handlers or confer permission.

**RM10-UI-02 Logical catalog.** Management MUST present one logical catalog entry for a registered definition, with separately retained observations of participating instances and their supported versions. A later instance registration MUST NOT silently replace another version's schema or change the editor for existing configuration. Definition conflicts MUST be reported explicitly. An ordinary presence report cannot create trusted schema authority. The implementation MUST extend the existing trusted catalog and deployment provisioning mechanism, retaining independently authorized definition and version changes.

**RM10-UI-03 Configured instances.** The calendar provider MUST support creating named configured trigger instances from its registered capability. Other providers MUST declare whether operators may create additional instances, edit an existing instance, or inspect a fixed source only. The portal MUST expose only supported operations. Job implementations remain application registrations; choosing a job or creating a Scheduled Task MUST NOT create a new executable handler or clone a registered job implicitly.

**RM10-UI-04 Form description.** The first implementation MUST render ordinary text, numeric, Boolean, enumeration, duration and grouped object fields, together with the calendar controls required by the accepted schedule descriptors. Portable form hints MAY declare field paths, labels, descriptions, groups, order, units, read-only presentation and a supported editor identifier. Hints MUST refer to declared fields and supported components. They MUST NOT carry executable code, React components, CLR type selectors, arbitrary scripts or arbitrary service URLs. A specialized new interaction requires an explicitly supported portal component.

**RM10-UI-05 Configuration versus input.** Persistent trigger settings, persistent job settings and the input for an individual invocation MUST have distinct contracts. A Scheduled Task supplies the selected trigger, selected job, resource resolution and input mapping. Framework execution context, including event, task, occurrence and attempt identities, MUST be populated by the trusted runtime. A result summary contract MUST describe safe bounded result fields; it is not permission to serialize arbitrary application objects into history.

**RM10-UI-06 Lookups and mapping.** A form MAY reference a registered named lookup that returns authorized choices for its declared owner and resource scope. Management MUST resolve the actual lookup target and authorization; form metadata cannot select an arbitrary network endpoint. Input mappings MUST initially support compatible event fields, configured constants/defaults and registered typed mappers. Admission-side mappers MUST be bounded deterministic adapters available in the authoritative admission host; atomic fanout MUST perform no mapper network calls or dynamic loading of application code. Unsupported mapper identities MUST block task activation. Required target fields, nullability, format and resource constraints MUST be checked. Transformations such as deriving a business date from an instant require a declared mapper and explicit time-zone semantics. RM10 MUST NOT introduce a general expression or rule language.

## 15. Scheduled Task editor

**RM10-UI-07 Accepted structure.** Scheduled Task MUST be the main item being configured. Its task-level settings MUST include name, enablement, selected trigger, selected job, target resource or resource resolver, and invocation input mapping. The configuration editor MUST contain exactly two contextual tabs, **Trigger** and **Job**. The selectors exist at task level only. Both tabs MUST derive their selected identity, owner and configuration from that same task draft. The earlier three independent Trigger, Job and Link editors are superseded by this structure.

**RM10-UI-08 Selection consistency.** Changing the selected trigger or job MUST immediately update the corresponding tab's title, owner, supported fields and input-contract context. Draft values MUST remain associated with their definition/schema and selected configuration; values from one job cannot migrate into another job's settings. Task identity and name MUST remain stable unless explicitly edited. Compatible mappings MAY be retained after validation. Incompatible mappings MUST be cleared or visibly marked unresolved, and publication MUST reject an unresolved required mapping.

**RM10-UI-09 Configuration scope.** The Trigger tab MUST identify the selected configured trigger and whether its settings are shared by other tasks. The Job tab MUST distinguish application job defaults from task-specific inputs and explicitly supported overrides. The whole-task preview MUST identify which changes affect the task and which affect shared configuration, with authorized affected-task information when available. Editing or disabling one task MUST NOT silently disable, duplicate, rename or rewrite its referenced trigger or job. A user lacking permission to edit a shared object may still inspect the permitted task context.

**RM10-UI-10 Whole-task preview.** Preview MUST cover the complete draft from either tab: selected identities, owner/environment/resource, mappings, execution identity selection, proposed configuration changes and their scope. Preview MUST be side-effect-free and MUST NOT register a trigger event or run a job. Calendar preview MUST use the authoritative calendar evaluator and display the configured time zone and next firing instants. Event-driven triggers MUST show event-driven behaviour rather than a fabricated next firing time. Unsupported or unavailable preview capabilities MUST be represented explicitly.

**RM10-UI-11 History and execution identity.** History MUST be a separate view or action for the Scheduled Task, preserving the two contextual configuration tabs. Each logical run MUST open its attempts and identity details as defined by the history requirements. A job-level view MUST aggregate the same records across tasks. The task MUST show its inherited execution identity when only the application workload identity is supported. A selector is permitted only for approved alternatives supported by the selected job/application and authorized for the operator. Changing the job MUST revalidate that selection.

## 16. Publication and adoption

**RM10-UI-12 Reuse Configuration.** Persistent trigger and job settings MUST use the existing RM08 source publication, coherent release, assignment and owner-adoption mechanisms. RM10 MUST provide its authoritative management operations for task associations and their cross-contract validation. Those operations MUST reuse the existing authorization, original-operation, revision-precondition and Audit conventions. Runtime event, run and attempt records remain scheduler persistence. A form descriptor is not another configuration store or a new authority over application settings.

**RM10-UI-13 One coherent reviewable change.** The portal MAY present a single Publish and apply action for a whole-task draft while performing the required underlying operations. Every mutation MUST retain its original idempotency identity and exact preconditions through recovery. Changes owned by different modules or databases MUST NOT be represented as one distributed transaction. If publication succeeds but assignment or task activation does not, the UI MUST report the actual completed and outstanding parts. Retrying MUST recover those operations rather than duplicate successful effects.

**RM10-UI-14 Revision activation boundary.** A task revision MUST bind exact accepted references for its trigger/event contract, job/input and execution/recovery contracts, resource mapping, execution profile and configuration required to construct an occurrence. Publishing desired configuration is distinct from accepting the executable task revision. A new revision MUST remain pending while required validation or adoption is unresolved. The previously active revision remains authoritative until an explicit successful promotion or disablement. Event admission MUST observe one active revision and a coherent configuration snapshot, never a mixture assembled from independently changing latest values. This requires no claim that every instance adopts simultaneously.

Adopting changed shared trigger settings or job defaults MUST initiate revalidation of every affected task and derive the corresponding executable task revisions without changing their stable TaskIds or unrelated mappings. Promotion MUST respect current task preconditions and required owner adoption; an automatic update cannot overwrite a concurrent user edit. The UI MUST expose each affected task's pending, rejected or active configuration references. Shared edits cannot leave other affected tasks permanently pinned without a visible pending or refused result. Active source and task revisions MUST remain compatible throughout promotion: a trigger change that would invalidate active event bindings stays pending until the authority can activate a coherent compatible set or the affected tasks are explicitly disabled. This authority-side rule does not imply a distributed transaction across configuration owners.

**RM10-UI-15 Future work and existing runs.** A successful activation affects events accepted after its authoritative activation boundary. Already accepted events and queued occurrences MUST retain their captured task revision, mapping, input, execution settings, detached business settings and authorization intent, subject to the independent current execution gates. RM10 MUST add a typed context or adapter through which the handler obtains its captured business settings and exact version. This does not change the semantics of an existing live `IConfigurationObject` or temporarily replace its global value during replay. New shared settings affect future occurrence admissions as the affected executable task revisions are promoted under UI14. A source event received after an outage is evaluated under the active task revisions at durable event acceptance, not reconstructed historical portal state. Explicit cancellation or retirement follows the core lifecycle; ordinary configuration edits MUST NOT rewrite historical execution context.

**RM10-UI-16 Honest adoption status.** The portal MUST distinguish published desired configuration, active task revision, owner-applied configuration and historical successful adoption. It MUST display pending validation/adoption, rejection, restart requirement, stale/offline observations and no eligible instance where applicable. Publishing while an owner is unavailable MAY proceed within RM08's actual rules; it does not establish owner acceptance or execution readiness. Security profile, trust and grant changes MUST honour RM01's existing restart/replacement policy. A configuration notification or cached Ready observation does not authorize execution.

**RM10-UI-17 Validation layers.** The browser MUST provide immediate checks for declared field rules. Management MUST validate the actual permissions, schemas, source/target contracts, mapping, resource scope and current preconditions. The owning module MUST perform its typed and business validation before adoption. A successful structural preview MUST NOT be described as proof of deployed semantic acceptance. Optional owner validation capabilities MUST be side-effect-free. Unsupported owner validation or unavailable dependencies MUST produce a precise pending or refused result rather than a fabricated success.

**RM10-UI-18 Protected content and conflicts.** Definition discovery, values, defaults, input samples, result details, lookup choices, impact previews and history MUST each respect their actual access scope. Redacted or unavailable content MUST NOT be represented as empty configuration, absence or a reset to defaults. Editors MUST preserve unrelated members and inherited settings according to the existing Configuration contract. A concurrent-edit precondition failure MUST retain the draft, show the current authoritative revision and require reconciliation before applying the intended change; it MUST NOT silently overwrite another operator's work.

## 17. Management API and portable clients

**RM10-UI-19 Bounded operation groups.** RM10 MUST expose authenticated, portable management operations sufficient to discover registered capabilities and configured triggers/jobs; inspect supported schemas and configuration status; create or revise supported trigger configurations and Scheduled Tasks; validate/preview task mappings and calendars; enable, disable or retire a task; request an explicitly supported manual event/run or cancellation; inspect events, runs and attempts; and recover uncertain mutations. Configuration value publication MUST continue through RM08. Exact HTTP route names and DTO members belong in the checked-in portable contract during implementation.

**RM10-UI-20 Existing protocol conventions.** APIs MUST extend the existing Management service and typed C# and TypeScript clients compatibly. They MUST retain bounded requests, payloads and pages; strict command validation; explicit unsupported/unknown response interpretation; exact identity comparison; and lossless representations for revisions and counters that exceed JavaScript integer precision. Authorization MUST apply to each real resource, page, lookup and recovery request. Responses MUST preserve known rejection, noncommit, unknown commit, original committed outcome and current cleanup observations distinctly.

**RM10-UI-21 Actions and recovery.** Run now and cancellation are operational commands, not temporary configuration edits. Manual execution MUST follow the same durable admission, identity, mapping and ownership rules as other runs. Repeating the same accepted command with the same original identity MUST recover its existing result. An uncertain response or a NotFound recovery observation MUST NOT automatically authorize another-key submission. The UI MUST retain command identity while the result remains unresolved and present the actual outcome without claiming that a requested cancellation stopped code.

**RM10-UI-22 Composition and delivery ownership.** RM09 owns the common renderer, field components, calendar editor and presentation of publication/adoption status. RM10 owns the trigger/job/task descriptors, compatibility rules and scheduler-specific operations. Owning modules own semantics and actual adoption; RM08 owns configuration distribution. This interface split MUST permit backend, descriptors and portal integration to progress against versioned contracts while ongoing roadmap work is reconciled. A new dependency or frontend package MUST follow the repository's existing dependency policy rather than being implied by form generation.

Its task-level selectors, coherent mapping, two contextual tabs and whole-task preview MUST be preserved. The existing prototype is an explanatory reference, not a production component or a dependency on its local file path. The specification and acceptance criteria MUST remain sufficient when the prototype is unavailable.

**RM10-UI-24 Review only uncovered design work.** CIS MUST prepare a concrete, reviewable design for new History and execution-identity surfaces, or material departures from the accepted editor, before implementing those uncovered visual decisions. Obtain the design approval required by the existing RM09 process where that approval has not already been given. Do not request another approval merely to repeat the accepted layout, implement its backend contracts, perform routine styling, or run focused validation. Backend and contract work may proceed independently of that remaining visual review.

## 19. Capacity and operational profile

The following values define the initial profile. They are ceilings, and the effective limit is the strictest applicable enclosing Messaging, Configuration, transport or host limit. All complete encoded envelopes and complete admissions must be checked; individually valid fields do not guarantee that their combined envelope fits. Supported overrides must remain finite and must preserve published protocol compatibility.

| Setting | Initial value or requirement |
| --- | --- |
| Configured triggers per authority and environment | 1,024 |
| Scheduled Tasks per authority and environment | 4,096 |
| Unsettled runs per authority and environment | 10,000, subject to the storage quota and completion reservation |
| Active tasks selected by one event | 64 |
| Input mapping entries per task | 64 |
| Encoded trigger payload | 64 KiB |
| Encoded job invocation input | 64 KiB |
| Captured business settings | 64 KiB |
| Complete persisted execution capsule per run | 256 KiB |
| Complete event admission payload including fan-out capsules | 4 MiB |
| Scheduler-specific HTTP body ceiling | 1 MiB; existing unrelated endpoint limits remain unchanged |
| Structured JSON depth | 16, or a stricter existing limit |
| Result summary | 16 KiB within its enclosing limits |
| Page size | 100 by default, 500 maximum where the underlying endpoint supports it |
| Due-event scan or reconciliation batch | At most 100 records before yielding |
| Business retry | Disabled by default; explicit retry profile uses three total attempts, with a supported maximum of 16 |
| Dispatch and recovery backoff | Five-second initial delay, sixty-second ceiling, bounded jitter |
| Detailed terminal history | 30 days |
| Daily aggregate history | 180 days |
| Ordinary progress publication | At most one update per attempt per five seconds; terminal reporting is separate |
| Scheduler logical storage quota | An explicit positive deployment value is required when production scheduling is enabled; there is no unlimited mode |
| Existing local execution and coordination bounds | Retain the selected RM05 limits; central quotas do not redefine local limits or create distributed category quotas |

**RM10-OPS-01 Complete reservation.** Admission MUST account for complete event/run data and conservatively reserve bounded capacity for the permitted attempts, outcome reconciliation and completion of that accepted work. Failed reservations leave no partial accepted fan-out. Ordinary progress is coalesced, and unchanged recovery polls do not append attempt rows. A record cannot grow without bound because a dependency is unavailable. At capacity, reject new responsibility with a structured retryable result while allowing the already admitted settlement and recovery paths to proceed.

**RM10-OPS-02 Storage accounting.** The selected backend MUST document logical accounting, protected references, pruning and the relationship to physical database/index/WAL usage. A logical quota is not a promise of identical physical disk consumption. Reuse existing quota and persistence patterns. No background cleanup may remove protected pending work, required original-result evidence or a receipt still needed for permitted replay. If a safe expiry cannot be proved, retain the compact protection and refuse additional admission rather than silently weakening duplicate protection.

**RM10-OPS-03 Fair bounded processing.** Producers, dispatch adapters and cleanup use bounded batches, yield between batches and honour cancellation and actual lifetime settlement. Retained run readiness and retry decisions survive restart. Idle trigger/job definitions must not each create a thread, permanently occupied callback or continuous log stream. Define any ordering provided within a task/resource; global fairness, global FIFO and distributed category quotas are not implied by RM05 exclusivity.

**RM10-OPS-04 Observation integration.** Reuse existing Logging, Metrics and Healthcheck. Record meaningful event-admission outcomes, pending/running counts, execution outcomes/durations, reporting freshness and capacity refusals. Metrics include the existing application/environment identity and only bounded approved dimensions. EventId, RunId, TaskId, ResourceId, arbitrary exception text and correlation identifiers must not become unbounded metric labels. Logs and history may carry bounded correlation identifiers. Health and metric reads use cached observations rather than querying or mutating the scheduler store.

**RM10-OPS-05 Operational status.** An unavailable portal, idle calendar, ordinary standby contention or a disabled task is not itself a failed application. Expose source/store availability, paused production, pending work, outcome uncertainty and stale reporting distinctly. An operational status read must not perform event production, adoption, lease renewal or business work. Report the actual failure and recovery boundaries supported by the selected provider.

## 21. Implementation handoff and completion

**RM10-DEL-01 Reconcile the actual checkout.** On implementation, inspect the current repository instructions, module contracts, accepted RM09 design and ongoing work before selecting public names and file locations. Record the actual source baseline once. Reconcile additive integration against the actual RM01–RM09 APIs; do not implement from obsolete planning signatures. Preserve unrelated ongoing work and use isolated branches/worktrees where needed.

**RM10-DEL-02 Use CIS as the work owner.** Import this complete specification as authoritative input through the supported CIS workflow. Declare responsible components and connect requirements to stories, tasks, source and acceptance evidence using supported traceability relationships. Keep stories at most medium-sized and give tasks concrete acceptance. Parallelize independent contract, backend, consumer and approved UI work after their shared boundaries are agreed. Do not invent CLI commands, a second planning ledger or synthetic graph links to conceal unsupported traceability.

**RM10-DEL-03 Focused verification.** Reuse CommonTesting, controllable time and the repository's existing Testcontainers/native PostgreSQL, RabbitMQ and HTTPS fixtures as applicable. Unit substitutes prove logical behaviour; actual multi-instance arbitration, locking, authentication, acknowledgement loss and delivery need real-provider evidence. Use representative interaction and boundary cases from the acceptance table, not exhaustive permutations, mutation campaigns or another custom harness. Run wider regression only for a concrete dependency impact or required repository gate. Keep summaries and necessary checkpoints; do not accumulate large evidence archives.

**RM10-DEL-04 Deliverables.** Deliver production provider/adapters, portable contracts and conformance examples, compatible C# and TypeScript clients, approved portal surfaces, one maintained consumer recipe, migration/deployment instructions and operational guidance for pause/recovery/retention. Public injectable ports and useful CommonTesting substitutes must cover trigger submission, task/run observation and controlled scheduling without exposing provider internals. Documentation must explain source ownership, actual durability, authority boundaries and the result of unavailable dependencies.

**RM10-DEL-05 Completion evidence.** Closeout MUST identify implemented requirements, actual acceptance results, the qualified commit and material residual limitations. Authoring a test, displaying a mockup or compiling a client does not establish native execution or UI integration. Complete the existing required build/compatibility gates and native provider scenarios for the selected implementation.
