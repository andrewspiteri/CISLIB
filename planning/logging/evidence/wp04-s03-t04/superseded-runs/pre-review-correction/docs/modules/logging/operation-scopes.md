# Operation scope foundation

WP04-S03-T01 implements the caller-owned `CIS.Logging.OperationContextData` input and internal `CIS.Logging.Scopes.OperationScopeStore`. A future CoreLogRuntime owns one store; actual runtime construction, admission/closure and its public BeginScope method remain later integration work. This helper creates real scopes without starting logging or reading startup configuration.

The input exposes nullable OperationId and IReadOnlyDictionary<string, LogValue> Attributes, matching the preserved reference surface. BeginScope reads the input properties once, trims the optional identifier, treats blank as absent and rejects retained malformed/control text or more than 255 Unicode scalars. Identifiers are correlation values and are never silently clipped. Null attributes become an empty map. LogValue.Map copies the caller dictionary, uses ordinal keys and applies the existing root-inclusive 1024-node/depth-8 projection. Immutable LogValue children may be shared; caller maps, DTOs and mutable source arrays are not retained. Existing and newly observed truncation remain on the captured map for later merged/event capture.

Each store has its own AsyncLocal slot. The slot points to an immutable frame with copied payload, immutable parent link and cached depth. BeginScope replaces the current flow's head; it does not mutate an inherited frame or a shared environment identity. Child tasks inherit normal execution context; their own pushes/pops leave the parent and sibling heads unchanged. Suppressing execution-context flow suppresses inheritance. [Microsoft's AsyncLocal documentation](https://learn.microsoft.com/dotnet/api/system.threading.asynclocal-1) describes context propagation, and [the CLR implementation](https://source.dot.net/System.Private.CoreLib/src/runtime/src/libraries/System.Private.CoreLib/src/System/Threading/ExecutionContext.cs.html) shows immutable execution-context capture and replacement.

The initial helper enforces depth 32 before traversing content, captures before publishing, allocates the handle before changing the head and rejects a stale parent if a cooperative map enumerator re-enters scope creation. Input callback cost, failures and deliberate callback side effects are caller behavior, as with existing value factories. A failed outer capture does not overwrite a newer head.

Normal LIFO disposal restores the prior head; initial guards reject an ancestor's out-of-order disposal without mutation and permit repeated disposal after a completed pop. Handles must stay in their creating logical flow and must not be passed to another concurrent flow. T01 evidence did not claim universal cross-flow rejection: inherited parent and child heads can share the same frame. During T03 the user retained the original creator-disposes rule and approved documenting detection limits, withdrawing our later unpublished stronger promise. Historical evidence and original supplied plans remain unchanged; the effective draft runtime contract follows that selected amendment.

## Merged scope capture (WP04-S03-T02)

OperationScopeStore.Capture reads the current immutable head once and returns an internal CapturedScopeContext. Empty/single-scope views reuse safe immutable attributes; a multi-scope view visits copied frames from outer to inner. Last ordinal key wins as a complete typed value, including explicit null. Case variants and reserved-looking keys remain distinct ordinary attributes. The innermost nonblank captured OperationId wins; an absent ID does not erase an outer ID. This view contains owned values and cached scope depth, with no store or frame references. Later input mutation, scope disposal, replacement or child-flow changes do not alter a captured view.

Merge resolves winners before final root projection. It keeps at most 1023 distinct candidate keys, chosen at first encounter from outer to inner, while continuing through every bounded frame to resolve later duplicates of those candidates. Excess new keys are omitted with truncation recorded. Within each frame and the final map projection, selection follows the captured dictionary's enumeration order. The qualified .NET 10 behavior is pinned by native prefix tests; insertion/member order is not a portable or public API contract. The observer sorts its reported case-key list ordinally, and negative controls change membership rather than order. This avoids constructing a full oversized secondary dictionary from all 32 scope maps. Final LogValueProjection applies its independent root-inclusive 1024-node/depth-8 budget; repeated immutable subtrees count per occurrence. Every already-recorded scope loss is carried into the final map, including when an inner scope replaces all retained truncated content.

The existing BeginScope depth guard admits exactly 32 levels and rejects the 33rd before reading identity or attribute content, without changing the current head. Capture itself leaves scope state unchanged. Native cases cover empty and all eleven value kinds, absent/trimmed IDs, ordinal keys across cultures, independent budgets, last-position overrides after candidate saturation, inherited loss, snapshot independence, child/store isolation and depth boundaries. Four exact-runtime subprocess scenarios observe actual Core precedence, candidates, inherited loss and depth. ## Creator-owned disposal (WP04-S03-T03)

The user selected BeginScope and the creator-disposes rule on 11 October 2026. The creating method keeps its handle and disposes scopes in reverse order, normally with a using declaration around awaited work. A child inherits copied scope values and may open/dispose its own scopes; the parent's handle must not be transferred to the child. The scope API remains the planned IDisposable BeginScope surface; the actual public runtime is integrated later.

OperationScopeStore retains its existing bounded stack algorithm. A matching head is popped to its exact immutable parent. A non-head ancestor raises InvalidOperationException without changing the head. An absent frame whose handle has never completed disposal in any flow also raises InvalidOperationException unchanged, with the message "The operation scope is not active in the current asynchronous context." Repeated valid owner disposal after a completed pop leaves the current head intact, including while a later scope with identical values is active. Error message text is a qualified C# diagnostic observation, not a portable ownership identity.

The per-handle completion flag is shared idempotence state; it does not identify the creator. These state guards detect some invalid uses. Other cross-flow transfer/disposal is prohibited with unspecified behavior and no universal detection promise. In particular, inherited head identity, captured ExecutionContext identity, AsyncLocal tokens, thread IDs and task IDs cannot establish ownership. Prohibited child pops can set that completion flag. A previously captured context can retain an old frame after the owner pops, so restoring it and disposing the handle can change that stale view. Such calls are outside the valid owner-repeat guarantee. No simultaneous cross-flow disposal atomicity is promised.

Open and close the scope in the same logical method. Beginning a scope inside an async helper and returning its handle does not install the helper's frame in its caller; keep the awaited work and disposal inside that helper instead. Unawaited child work can retain the inherited OperationId/attributes after the parent's lexical scope ends. A parent's pop does not clear a child's inherited view, and a child's own push/pop leaves the parent intact. Await child work before ending the intended operation lifetime.

Native valid-use controls cover every ancestor at depths 2, 8 and 32, exact restoration after every pop, repeated errors followed by cleanup, completed handles beside identical replacement scopes, await/ambient changes, child-owned scope cleanup and independent stores. Additional detectable-state cases verify safe errors and preservation of the never-completed absent-frame guard. Four process scenarios qualify actual Core LIFO, repeats, awaits and absent-frame errors. The earlier ownership/lifetime probes are separately labeled investigations: acceptance of prohibited misuse is never counted as a passing requirement. Direct and fresh-copy Developer verification pass 2482 unit, 352 integration and 393 architecture cases (3227 total, no failures or skips), including twelve new unit rows, four integration rows and all 55 compiler controls. Four actual disposal scenarios pass on Windows and Ubuntu with identical managed process inputs and exact .NET 10.0.12/no roll-forward. Claude source review passes and required evidence-helper findings are resolved in the corrected follow-up. [Retained T03 evidence](../../../planning/logging/evidence/wp04-s03-t03-windows-linux.json) separates the final candidate from superseded ownership/lifetime investigations and records reviewed source, native results, process identities and copied-source verification. T03 is complete under the user-selected contract; T04 shared-story qualification, event/runtime integration and release remain later work.

## Complete scope scenarios (WP04-S03-T04)

The [shared scope catalog](../../../conformance/logging/scope-qualification-cases.json) describes fourteen literal scenario results for nested depths 2/32, inherited child scopes, two/eight overlapping operations, two/four independent stores, cancellation during an await or after release, mutable dictionaries/read-only wrappers and invalid order at depths 3/32. The [acceptance map](../../../conformance/logging/scope-qualification-map.json) preserves all four original criterion descriptions and states their internal scope-state meaning. Runtime-owned store isolation is qualified here; actual CoreLogRuntime wiring, provider scopes, shared environment/event integration and encoded-entry bytes remain later work.

Each worker signals readiness after opening its own scopes. The controller observes its parent heads before releasing work, mutates caller input or cancels the caller token at that boundary, releases workers and joins them before disposing its own handles. Results use descriptor index order rather than completion order. There are no sleeps or owner-identity heuristics. Error paths release all gates and join workers with explicit deadlines, preserving readiness/worker failures. Cancellation is a real exception through a using scope, with the actual caller token checked; the store itself does not accept a cancellation token.

Mutation observations distinguish BeginScope copying of DTO/dictionary state from earlier LogValue ownership of nested construction inputs. The observer reports actual Core IDs, merged values, cached scope depth/loss and exact frame restoration. Its JSON is a development transport, not the shipping event format. Native exception names/messages are separate C# bindings. C# and Python compare the complete expected tree and reject changed IDs, values, participant order, depth, types and missing fields. Accepting prohibited cross-flow disposal remains outside conformance.
