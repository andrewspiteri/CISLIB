# CisLib

CisLib is a reusable, multi-module core library with shared contracts, examples, instructions and agent skills. Logging is the first module, and C# is the first implementation. Additional languages will have their own implementations and build tools while sharing the applicable module contracts and conformance cases.

The repository currently contains tested configuration resolution/validation and the actual [C# EnvironmentOptions startup API](docs/modules/logging/environment-options.md), alongside [typed C# log values](docs/modules/logging/log-values.md), the internal [exception capture foundation](docs/modules/logging/exception-projection.md) and [bounded JSONL event encoding](docs/modules/logging/event-encoding.md), test projects and executable dependency checks. Shared startup/event/runtime contracts remain unpublished. The bounded logging runtime and Microsoft logger integration are implemented and qualified through their runtime/provider stories. Both ship in `CIS.Core`, using the `CIS.Logging` and `CIS.Logging.MicrosoftLogger` namespaces; [Microsoft logging packaging](docs/modules/logging/microsoft-logging-packaging.md) explains the approved dependencies. ConsoleHuman is still an example scaffold; runnable package examples, instructions/skills and complete release qualification remain pending.

## Start with C#

Install .NET SDK **10.0.401** and PowerShell 7. Run from the repository root:

```powershell
pwsh -NoProfile -File eng/verify.ps1 -Profile Developer
```

The developer check restores locked dependencies, evaluates project/package boundaries, checks formatting, builds Release, inspects built/packed assembly references, runs the populated unit, integration and architecture suites and starts the console host. This verifies the foundation, not the complete logging release suite. Run the individual steps from `implementations/csharp` when working in an IDE:

```powershell
dotnet restore CisLib.slnx --locked-mode
dotnet build CisLib.slnx -c Release --no-restore
dotnet run --project examples/logging/ConsoleHuman -c Release --no-build
```

The separate toolchain qualification command uses a fresh source copy, CLI home and NuGet cache, executes Microsoft coverage and isolated Stryker, checks API compatibility controls, and retains native reports and prerequisite archives:

```powershell
pwsh -File implementations/csharp/eng/verify-toolchain.ps1
```

It also requires .NET runtimes **10.0.12** and **8.0.31**, Git, and HTTPS access to NuGet. Read [C# toolchain qualification](docs/architecture/csharp-toolchain.md) for exact pins, scope and retention limits.

Open [CisLib.slnx](implementations/csharp/CisLib.slnx) for the C# solution. The root [eng/verify.ps1](eng/verify.ps1) dispatches to the initial C# verification lane.

The [verification and source replay guide](docs/architecture/csharp-verification.md) explains structured reports, all six family slots and the required-case inventory. Validate existing Developer evidence with `pwsh -File eng/check-release.ps1 -Profile Developer`, or rebuild it with isolated caches using `pwsh -File eng/replay.ps1 -Profile Developer`. Release verification and replay remain nonzero until their required implementation and evidence exist.

Read the [startup, identity and configuration contract](docs/modules/logging/startup-contract.md) for `CIS.EnvironmentOptions`, immutable outputs and configuration precedence. The current readonly static container supersedes historical startup publication mechanics.

## Executed gates

1. All registered evaluated projects, their target/packability, exact project edges, explicit package IDs and frameworks. Convenience frameworks such as ASP.NET cannot enter Core.

3. Packed dependency groups and versions, and a closed asset list. Bundled third-party/test DLLs, native assets and unapproved content/build scripts are rejected.
4. Compiled Core DLL references using .NET managed metadata APIs, without executing the inspected assembly. Allowed names come only from the SDK's resolved `Microsoft.NETCore.App` reference pack and approved runtime packages. The packed DLL must match the inspected build when both paths are supplied.

Normal developer verification runs every project gate before build, then checks the built and packed Core DLL. `-ProjectPath` scopes isolated negative-fixture checks to one already registered project; it does not alter the normal whole-manifest verification. `-LanguageRoot`/`-AssetsPath` permit copied fixture inputs rather than corrupting real source/restore data.

A NuGet dependency written as `10.0.12` is an inclusive minimum, not an exact `[10.0.12]` restriction. The current nuspec keeps that minimum-version syntax. Repository verification pins the actual restored closure at 10.0.12 with its lock files and allowlist; it does not claim every application's dependency graph is locked by Core's nuspec. See [NuGet version ranges](https://learn.microsoft.com/en-us/nuget/concepts/package-versioning#version-ranges).

An application restoring only `CIS.Core` therefore receives the logging implementation, Microsoft adapter and approved abstraction dependency closure.
