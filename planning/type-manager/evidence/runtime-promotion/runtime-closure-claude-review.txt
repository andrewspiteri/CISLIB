## Mandatory (verification)

### V1 — Medium: `Replay-Consumer` overwrites `$Name`; the frozen-binary log and report names are wrong
`eng/check-type-manager-compatibility.ps1`, `Replay-Consumer`

PowerShell variable names are case-insensitive, and a `foreach` variable persists in the enclosing scope. `foreach ($name in @('CIS.Core.dll', …))` therefore reassigns the parameter `$Name`. After the loop, `$Name` is `'Microsoft.Extensions.DependencyInjection.Abstractions.dll'`. This has three effects:

- Both replays log to `Microsoft.Extensions.DependencyInjection.Abstractions.dll.log`. The `source-consumer` run overwrites the `frozen-binary` log.
- Both `results` entries are recorded with `name = 'Microsoft.Extensions…dll'` instead of `frozen-binary` / `source-consumer`.
- The checks still pass, because each run reads its log immediately. That is why the run reported success while its recorded evidence is misattributed and incomplete.

Fix: rename the loop variable (for example `foreach ($fileName in …)`), then rerun the compatibility replay to regenerate the report.

## Recommended runtime (Low, before baseline freeze)

### R1 — Report misclassifies a newly loaded assembly as reused when a dynamic assembly shares its identity
`TypeManager.cs`, the `initiallyLoaded` snapshot

The snapshot includes dynamic assemblies, while F4 excludes them from reuse. In the `dynamic-name-collision` scenario, the `AssemblyBuilder` is given v1's exact full name. The real v1 is then newly loaded and cataloged, but its identity appears in `ReusedAssemblyIdentities` and not in `LoadedAssemblyIdentities`. That contradicts the property docs and the F4 rule. Under TM10 it would become documented behaviour.

Fix: `.Where(assembly => !assembly.IsDynamic)` in the snapshot. In the `dynamic-name-collision` fixture, also assert that the v1 identity is in `LoadedAssemblyIdentities` and absent from `ReusedAssemblyIdentities`.

### R2 — A bind result from another load context is accepted
`SelectedAssemblyLoader.Load`, pass 2

For app-local assets that are not in the TPA, `LoadFromAssemblyName` raises `Default.Resolving` and `AppDomain.AssemblyResolve` before the `FileNotFoundException` fallback. A host handler may return a non-dynamic assembly from a custom or collectible ALC with the matching identity. That assembly passes `IsDynamic` and `ValidateIdentity` and gets cataloged. This contradicts the default-context invariant that `ValidateContract` enforces for queries.

Fix: extend the dynamic rejection to `loaded.IsDynamic || AssemblyLoadContext.GetLoadContext(loaded) != AssemblyLoadContext.Default`, using the same `AssemblyLoadFailure` mapping.
