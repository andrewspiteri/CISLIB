# Healthcheck v1 contracts

User-approved additive amendment (21 October 2026): detailed monitors may contain optional `registrationDiagnostic`, using the existing bounded diagnostic shape. Absence remains valid; explicit null is invalid. It records the monitor lifetime's latest accepted registration-scoped integration error in state commit order, independently of the health reason, collection error and execution-scoped errors. Success and unbinding an external monitor retain it. An identical normalized registration diagnostic event is Duplicate without another revision; a distinct accepted event replaces it. No public constructor, schema version or required field changes. Existing readers that ignore unknown optional fields remain compatible.

These are unpublished HC00 foundation contracts authored from the reviewed Healthcheck catalog. They are inputs for implementation and native verification. They are not evidence that a service, serializer, HTTP adapter, pipe server or probe has executed.

`report.schema.json`, `pipe-request.schema.json` and `pipe-response.schema.json` use JSON Schema draft 2020-12. Register all three schemas by their declared URNs in a local validator; the pipe response references the report URN. Validation requires no network resource. Unknown optional fields are accepted, while known fields retain their declared types and rules.

`configuration.json` records exact deployment keys, defaults, ranges, policy inputs, text budgets, CLI results and stable error codes. `HealthcheckOptions.Resolve` is an explicit environment-resolution operation. Construction starts no runtime and does not reread environment settings. Explicit identity requires Name and InstanceId; default identity remains a service projection of existing EnvironmentOptions facts.

The report root is either a snapshot or an HTTP/reporting error. Compact writers emit no monitors array. Details includes the complete array, ordered by registration ordinal; each monitor includes measurements ordered ordinally by key. A reader can accept an additive complete monitors array in compact input, but must validate any recognized details it consumes. The pipe envelope always has matching protocol/schema versions and exactly one snapshot or error. A null view is permitted only for an invalid or unparseable request.

All optional unavailable fields are omitted. Known fields do not use null placeholders, except the invalid-request pipe view. Unavailable measurements omit value; every other measurement has exactly its declared scalar type. Integers and lifetime counters use canonical decimal strings bounded to Int64. ExecutionId uses a canonical positive Int64 decimal string. Revision is an unbounded canonical unsigned decimal identifier and needs no client-side arbitrary-precision arithmetic. Durations use the source snapshot's measured monotonic values with wire names ending in Ms, never wall-clock subtraction.

UTC timestamp readers accept zero through seven fractional digits and a terminal Z; fixtures use seven digits. Readers must parse valid real dates, rather than relying only on the schema pattern or an optional format assertion. Every text limit counts Unicode scalar values. Explicit identity bounds are Name 1..255, optional BuildVersion and ServiceVersion at most 512 each, optional HostName at most 255 and optional OsDescription at most 1024. Optional monitor display names are limited to 128. Identity and direct scalar inputs require valid Unicode. Diagnostics sanitize malformed runtime exception text before emitting UTF-8; diagnostic free text can be scalar-truncated with isTruncated=true. Oversized direct structural codes/type identifiers are invalid. Diagnostic projection never carries stack traces or arbitrary owner objects.

Schemas cover structure and many scalar bounds. Native parsers and semantic validators must additionally enforce:

- Strict UTF-8, no BOM on output, no duplicate property names at any object depth, and a maximum JSON nesting depth of 16 including unknown fields. JSON object materialization must not erase duplicates before checking them.
- Four-byte unsigned little-endian framing, request payload 1..512 bytes, response payload 1..the selected MaxReportBytes, complete reads across arbitrary fragments and one exchange per connection. Reject truncation before treating a partial body as a report. Bound bytes/depth before allocating an object graph.
- Actual finite double decoding, canonical lower-case nonempty Guid values, valid Unicode scalar text and exact timestamp parsing. JSON Schema implementations that count UTF-16 units or accept isolated surrogates need the native scalar checks.
- Count bounds and relationships: critical, failing and pending do not exceed active; criticalFailing does not exceed critical or failing; failing plus pending does not exceed active; criticalFailing is at least critical plus failing minus active. Healthy is equivalent to criticalFailing=0. Ready equals startupCompleted AND NOT isStopping AND Healthy.
- For details, unique monitor identities, complete list/count agreement, unique measurement keys and key ordering, applicable policy subobjects, and actual policy/outcome consistency. Registration ordering is a service/writer obligation: the wire exposes no ordinal for a client to verify it independently. A compact response cannot prove omitted per-monitor facts. Configured MaxMonitors may be below the schema's absolute 65536 limit.
- Request/response view matching, null-view disposition, selected health versus readiness result, supported versions, error/snapshot exclusivity and a failing probe result for every reporting error. A failed or malformed response must never imply healthy.
- Collection/execution lifecycle consistency, positive non-wrapping execution IDs, monotonic durations and actual settlement facts. The schemas do not infer chronology or outcome arithmetic from wall-clock timestamps.

Report size is a complete encoded UTF-8 budget. Pipe-envelope overhead counts toward it. It is a formatter/transport obligation rather than a JSON Schema property. HTTP HEAD uses the same captured report/size/status decision as GET and suppresses the body. A reporting error is distinct from an ordinary unhealthy snapshot and cannot change monitor health.

The reserved HTTP paths are /_health, /_health/ready and /_health/details. Known paths are case-insensitive with one optional trailing slash. Health/details select aggregate health; readiness selects ready. GET/HEAD map selected success to 200 and selected failure to 500. Disabled details/unknown descendants return NotFound (404); unsupported methods on enabled known routes return MethodNotAllowed (405, Allow: GET, HEAD); denied details returns Forbidden (403). Details authorization failure is ReportingUnavailable (500). The reserved branch never invokes business middleware; /_healthcare is outside it. Normal/error responses use JSON and no-store/no-cache headers, with no exception details in transport errors.

Canonical inputs and rejection cases are under ../../../conformance/healthcheck/common. Their manifest distinguishes schema, semantic, parser and framing obligations. No schema-conformance or transport-runtime pass is claimed by authoring these files.
